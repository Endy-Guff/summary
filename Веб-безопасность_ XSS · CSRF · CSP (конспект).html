Конспект по веб-безопасности для Senior Frontend

XSS · CSRF · CSP

Три темы, которые связаны между собой сильнее, чем кажется: XSS ломает почти любую защиту (включая CSRF-токены), CSP — это защита в глубину именно от XSS, а CSRF живёт на границе того, как браузер отправляет куки. Разбираем каждую по схеме: что это → как влияет → как делают → как защищаться.

1. XSS (Cross-Site Scripting)

1.1 Что это

XSS — это инъекция, при которой атакующий заставляет браузер жертвы выполнить чужой JavaScript в контексте доверенного сайта (в его origin). Ключевое: код исполняется от имени сайта, а значит имеет доступ ко всему, к чему имеет доступ сайт — куки (не HttpOnly), localStorage, DOM, токены, возможность делать запросы к API с куками пользователя.

Корень проблемы всегда один: данные, которыми управляет злоумышленник, попадают в исполняемый контекст без корректного экранирования/санитизации.

1.2 Типы XSS

Reflected (отражённый)

Payload приходит в запросе (обычно query-параметр) и сразу «отражается» в HTML-ответе без экранирования.

https://site.com/search?q=<script>steal()</script>

Сервер вставляет q в страницу как есть → скрипт исполняется. Одноразовый: жертву нужно заманить по ссылке (фишинг, реклама). Не сохраняется.

Stored / Persistent (хранимый)

Payload сохраняется на сервере (комментарий, имя профиля, сообщение в чате, поле в БД) и отдаётся всем, кто откроет страницу. Опаснее всего: не нужна специальная ссылка, поражает всех посетителей, может превратиться в самораспространяющегося червя (как знаменитый Samy в MySpace).

Blind XSS — подвид хранимого: payload срабатывает не там, где введён, а в другом интерфейсе (например, в админке, куда попадают заявки поддержки). Атакующий не видит результат сразу.

DOM-based

Уязвимость целиком в клиентском коде. Сервер может вообще не участвовать — небезопасные данные из «источника» (source) попадают в опасный «сток» (sink) прямо в JS.

// source: location.hash → sink: innerHTML
document.getElementById('out').innerHTML = decodeURIComponent(location.hash.slice(1));
// site.com/page#<img src=x onerror=alert(document.cookie)>

Особенность: payload часто в #hash, который не отправляется на сервер, поэтому серверный WAF/логи его не видят.

Mutation XSS (mXSS)

Браузер при парсинге «мутирует» HTML, и то, что казалось безопасным после санитизации, после реинсёрта в DOM превращается в исполняемый код. Классическая головная боль для санитайзеров — поэтому не пишут свои, а берут проверенный DOMPurify.

1.3 Sources и Sinks (must-know для DOM XSS)

Источники (управляемые атакующим данные): location (href, search, hash, pathname), document.URL, document.referrer, window.name, postMessage data, данные из localStorage/sessionStorage, ответы API, document.cookie.

Опасные стоки (куда нельзя лить недоверенное):

Сток Почему опасен
element.innerHTML / outerHTML Парсит и исполняет HTML
document.write / writeln То же
eval, Function() Исполняет строку как код
setTimeout/setInterval со строкой Скрытый eval
element.insertAdjacentHTML Парсит HTML
location = ..., location.href = ... javascript: URI
a.href, iframe.src = javascript:... Исполнение по клику
element.setAttribute('onclick', ...) Инлайн-обработчик
jQuery.html(), $(userInput) Обёртки над innerHTML
Angular/Vue/React escape-hatches см. ниже

1.4 На что влияет (impact)

  • Кража сессии — document.cookie → отправка на сервер атакующего → захват аккаунта (если куки не HttpOnly).
  • Кража токенов из localStorage/sessionStorage (одна из причин, почему хранить JWT в localStorage спорно).
  • Обход CSRF-защиты — XSS выполняется в origin сайта, читает CSRF-токен из DOM и делает «легитимный» запрос.
  • Keylogging и фишинг — подмена формы логина, перехват ввода.
  • Действия от имени пользователя — перевод денег, смена пароля/почты, публикация.
  • Дефейс, редирект, майнинг, распространение (worm).
  • Полный захват клиентской сессии — по сути злоумышленник управляет вкладкой пользователя.

1.5 Как защищаться (по приоритету)

1) Контекстно-зависимое экранирование вывода. Экранирование зависит от того, куда вставляются данные:

  • HTML-контекст: <, >, &, ", ' → HTML-entities.
  • Контекст атрибута: обязательно кавычки + экранирование.
  • JS-контекст: нельзя просто вставлять в <script> — нужен JSON-энкодинг/экранирование.
  • URL-контекст: encodeURIComponent, плюс валидация схемы (запрет javascript:).
  • CSS-контекст: свои правила экранирования.

Одно универсальное экранирование не работает — контекст решает всё.

2) Использовать авто-экранирование фреймворков и не ломать его.

  • React: {value} в JSX экранируется автоматически. Дыра — dangerouslySetInnerHTML. Также опасны href={userUrl} (может быть javascript:) и рендер в ref-манипуляциях через innerHTML.
  • Vue: {{ }} экранирует. Дыра — v-html. Опасны динамические :href.
  • Angular: по умолчанию экранирует и имеет встроенный sanitizer. Дыры — [innerHTML] с обходом, bypassSecurityTrustHtml/Url/Script/ResourceUrl.

Правило: любой escape-hatch (dangerouslySetInnerHTML, v-html, bypassSecurityTrust*) — это место, где обязательна санитизация.

3) Санитизация HTML там, где реально нужен HTML от пользователя (комментарии, WYSIWYG).

import DOMPurify from 'dompurify';
el.innerHTML = DOMPurify.sanitize(userHtml);

Никогда не писать свой санитайзер и regex-«очистку» — mXSS и обходы съедят его.

4) Избегать опасных стоков. Вместо innerHTML — textContent. Вместо setTimeout("code") — setTimeout(fn). Никогда eval/new Function на пользовательских данных.

5) Валидация ввода по allowlist (не blacklist) — как дополнительный слой, но не как основная защита (основная — экранирование вывода).

6) HttpOnly-куки — JS не может прочитать такую куку, значит XSS не украдёт сессию через document.cookie. Плюс Secure и SameSite.

7) Trusted Types (Chrome/Edge) — политика, запрещающая передавать в опасные стоки обычные строки; только объекты, прошедшие через политику. Радикально убивает DOM-XSS.

Content-Security-Policy: require-trusted-types-for 'script';

8) CSP как защита в глубину — см. раздел 3. Если экранирование где-то пропустили, строгий CSP не даст инлайн-скрипту исполниться.

2. CSRF (Cross-Site Request Forgery)

2.1 Что это

CSRF заставляет аутентифицированного пользователя выполнить нежелательное изменяющее состояние действие на сайте, где он залогинен, без его ведома. Атака эксплуатирует то, что браузер автоматически прикладывает куки к запросу на сайт — независимо от того, с какой страницы этот запрос инициирован.

Ключевое отличие от XSS: при CSRF атакующий не исполняет свой код на сайте и не читает ответ (мешает Same-Origin Policy). Он лишь «вслепую» отправляет запрос, полагаясь на куки жертвы.

2.2 Предусловия для успешной CSRF

  1. Действие меняет состояние (перевод, смена пароля/почты, покупка).
  2. Аутентификация основана на куках (или Basic-auth), которые браузер шлёт автоматически.
  3. В запросе нет непредсказуемых параметров, которые атакующий не может угадать (то есть нет CSRF-токена).

Если хоть одно не выполнено — классический CSRF не проходит.

2.3 Как делают

GET (если действие меняет состояние через GET — грубая ошибка бэкенда):

<img src="https://bank.com/transfer?to=attacker&amount=10000">

Просто загрузка «картинки» отправляет запрос с куками жертвы.

POST через авто-сабмит формы:

<form action="https://bank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
</form>
<script>document.getElementById('f').submit();</script>

Жертва заходит на страницу атакующего — форма сабмитится сама, браузер приложил куки bank.com.

Важно: обычная HTML-форма может слать только application/x-www-form-urlencoded, multipart/form-data, text/plain. Чтобы отправить application/json, нужен fetch/XHR, а это уже упирается в CORS и preflight — что само по себе становится защитой (см. ниже).

2.4 На что влияет

Любое изменяющее действие: смена email/пароля (→ захват аккаунта), перевод средств, оформление заказа, изменение настроек приватности, добавление админа. Прочитать данные атакующий обычно не может (SOP не отдаёт ответ), поэтому CSRF — это про действия, а не про утечку.

2.5 Как защищаться

1) SameSite-куки (современная база).

Set-Cookie: session=...; SameSite=Lax; Secure; HttpOnly
  • Strict — кука не шлётся ни при каких кросс-сайт запросах (даже переход по ссылке). Максимальная защита, но ломает UX (перешёл по ссылке из письма — не залогинен).
  • Lax — кука шлётся при top-level навигации GET-ом, но не при кросс-сайт POST/img/fetch. Хороший баланс, сейчас это дефолт в Chrome. Убивает большинство CSRF из коробки.
  • None — шлётся всегда (обязательно с Secure). Нужно для намеренно кросс-сайтовых сценариев.

SameSite=Lax по умолчанию закрыл огромный пласт CSRF, но не заменяет токены полностью (edge-кейсы, старые браузеры, GET-эндпоинты, method override).

2) CSRF-токены (Synchronizer Token Pattern). Сервер генерирует непредсказуемый токен, привязанный к сессии, кладёт его в форму/страницу; клиент шлёт его обратно (в поле формы или заголовке); сервер сверяет. Атакующий не может узнать/угадать токен и не может прочитать его из чужого origin (SOP). Золотой стандарт для форм.

3) Double-Submit Cookie. Токен кладётся и в куку, и в тело/заголовок запроса; сервер сверяет их равенство. Не требует хранения на сервере (stateless). Нюанс: уязвим, если атакующий может установить куку на поддомен — поэтому используют подписанные/__Host- куки.

4) Проверка заголовков Origin / Referer. Сервер проверяет, что запрос пришёл со своего origin. Дёшево и эффективно как доп. слой; минус — Referer иногда режется прокси/настройками приватности, поэтому не единственная защита.

5) Custom-заголовок для JSON API + CORS. SPA, которая шлёт X-Requested-With или свой заголовок через fetch, автоматически защищена: кросс-сайтовый запрос с кастомным заголовком требует CORS-preflight, который сервер атакующего не пройдёт. Плюс JSON-эндпоинты нельзя вызвать простой HTML-формой.

6) GET никогда не меняет состояние. Все изменяющие операции — POST/PUT/PATCH/DELETE. Это архитектурная гигиена, закрывающая <img>-вектор.

7) Ре-аутентификация / step-up для критичных действий (смена пароля, перевод) — запросить текущий пароль или 2FA.

2.6 CSRF ⟷ XSS

Если на сайте есть XSS, CSRF-токены не помогают: злоумышленный скрипт исполняется в origin, читает токен из DOM и делает валидный запрос. Поэтому XSS — приоритет №1; без него CSRF-защита имеет смысл.

3. CSP (Content Security Policy)

3.1 Что это

CSP — механизм защиты в глубину: HTTP-заголовок (или <meta>), который говорит браузеру, откуда разрешено грузить и исполнять ресурсы (скрипты, стили, картинки, шрифты, фреймы, соединения). Главная ценность — резко снижает ущерб от XSS: даже если инъекция прошла, строгий CSP не даст исполниться инлайн-скрипту или загрузиться скрипту с чужого домена.

Задаётся заголовком:

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'

<meta http-equiv> тоже работает, но заголовок предпочтительнее (умеет frame-ancestors, report-to, применяется раньше).

3.2 Основные директивы

Директива Контролирует
default-src Фолбэк для всех *-src, если не заданы явно
script-src Откуда грузятся/исполняются скрипты (ядро защиты от XSS)
style-src Стили
img-src Картинки
connect-src fetch/XHR/WebSocket/sendBeacon
font-src Шрифты
frame-src Что можно вставлять во фреймы
frame-ancestors Кто может встроить нас во фрейм (анти-clickjacking, заменяет X-Frame-Options)
base-uri Ограничивает <base> (защита от подмены относительных URL)
form-action Куда можно сабмитить формы
object-src <object>/<embed> (лучше 'none')
report-to / report-uri Куда слать отчёты о нарушениях

3.3 Источники (значения)

  • 'self' — свой origin.
  • 'none' — ничего.
  • 'unsafe-inline' — разрешает инлайн-скрипты/стили и onclick. Убивает смысл CSP против XSS — избегать.
  • 'unsafe-eval' — разрешает eval/new Function. Избегать.
  • https://cdn.example.com — host-allowlist (хрупко: если на CDN есть JSONP/gadget — обход).
  • 'nonce-<random>' — одноразовое случайное значение на каждый ответ; исполняются только скрипты с этим nonce.
  • 'sha256-<hash>' — разрешить конкретный инлайн-скрипт по хешу.
  • 'strict-dynamic' — доверять скриптам, которые загрузил уже доверенный (по nonce/hash) скрипт; при этом host-allowlist игнорируется. Основа современного «строгого» CSP.

3.4 Nonce-based CSP (рекомендуемый подход)

Content-Security-Policy:
  script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';

<script nonce="r4nd0m" src="/app.js"></script>

Плюсы: не нужен 'unsafe-inline', не нужен хрупкий allowlist доменов, 'strict-dynamic' корректно разрешает динамически подгружаемые чанки. Nonce обязан быть криптослучайным и новым на каждый ответ — иначе бесполезен.

3.5 Частые ошибки и обходы

  • 'unsafe-inline' в script-src — сводит защиту от XSS к нулю.
  • Слишком широкий allowlist (https:, *, крупные CDN с JSONP) — атакующий находит на разрешённом домене endpoint, отдающий подконтрольный JS.
  • Забыли object-src 'none' и base-uri — векторы обхода через <object>/<base>.
  • Nonce переиспользуется между запросами — предсказуем.
  • Только <meta> — нет frame-ancestors/reporting.
  • CSP не защищает от логических дыр, CSRF, утечки данных — это узкий инструмент против инъекции ресурсов, а не серебряная пуля.

3.6 Внедрение без боли

  1. Начать с Report-Only — ничего не блокирует, только шлёт отчёты: 
    Content-Security-Policy-Report-Only: script-src 'nonce-...' 'strict-dynamic'; report-to csp-endpoint
  2. Собрать нарушения, вычистить инлайны и внешние источники.
  3. Переключить на боевой Content-Security-Policy.
  4. Держать report-to включённым и в проде для мониторинга.

3.7 Clickjacking (бонус, тесно связан с CSP)

Атака, где ваш сайт грузят в невидимый iframe поверх «наживки», и жертва кликает по вашим кнопкам вслепую. Защита:

Content-Security-Policy: frame-ancestors 'none';   # или 'self'
X-Frame-Options: DENY                               # легаси, для старых браузеров

4. Как всё связано (карта в голове senior)

  • XSS — исполнение чужого кода в вашем origin. Самая опасная: ломает и SameSite, и CSRF-токены (код-то «свой»).
  • CSP — не предотвращает инъекцию, а ограничивает ущерб от XSS: инлайн/чужой скрипт не исполнится. Защита в глубину, не замена экранированию.
  • CSRF — про автоматическую отправку кук браузером. Лечится SameSite + токенами, но при наличии XSS теряет смысл.
  • HttpOnly отделяет куки от JS → XSS не украдёт сессию. Secure → только по HTTPS. SameSite → анти-CSRF.
  • Правильный порядок приоритетов: сначала убить XSS (экранирование + фреймворк + DOMPurify + CSP + Trusted Types), потом закрыть CSRF (SameSite + токены), потом clickjacking (frame-ancestors).

5. Быстрые чек-листы

XSS

  • Вывод экранируется контекстно (HTML/attr/JS/URL/CSS).
  • Авто-экранирование фреймворка не отключено без нужды.
  • Каждый dangerouslySetInnerHTML/v-html/bypassSecurityTrust* санитизирован DOMPurify.
  • Нет eval, new Function, setTimeout("string"), недоверенного в innerHTML.
  • URL валидируются (нет javascript:).
  • Куки HttpOnly; Secure; SameSite.
  • Внедрён строгий CSP (nonce + strict-dynamic).
  • (Опц.) Trusted Types включены.

CSRF

  • Куки сессии SameSite=Lax/Strict.
  • CSRF-токен на всех изменяющих формах.
  • GET не меняет состояние.
  • JSON API + кастомный заголовок / проверка Origin.
  • Ре-аутентификация на критичных действиях.

CSP

  • script-src без 'unsafe-inline'/'unsafe-eval'.
  • nonce криптослучайный и новый на каждый ответ.
  • object-src 'none', base-uri 'none', frame-ancestors.
  • Начали с Report-Only, включён report-to.
