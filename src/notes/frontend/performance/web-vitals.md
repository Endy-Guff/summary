# Web Vitals — конспект для senior frontend (React / Next.js)

## 1. Что такое Web Vitals

Web Vitals — это набор метрик от Google, которые измеряют, насколько **реальному пользователю** удобно на странице. Не «как быстро отработал сервер», а «как быстро человек увидел контент, смог кликнуть и не промахнулся из-за прыгающей вёрстки».

**Core Web Vitals (CWV)** — это три главные метрики из этого набора. Именно их Google использует как сигнал ранжирования в поиске:

| Метрика | Что измеряет | Простыми словами | Good | Needs improvement | Poor |
| --- | --- | --- | --- | --- | --- |
| **LCP** (Largest Contentful Paint) | Загрузку | Когда показался самый большой кусок контента | ≤ 2.5 с | 2.5–4 с | > 4 с |
| **INP** (Interaction to Next Paint) | Отзывчивость | Как быстро страница реагирует на клик/тап/клавишу | ≤ 200 мс | 200–500 мс | > 500 мс |
| **CLS** (Cumulative Layout Shift) | Визуальную стабильность | Насколько сильно прыгает вёрстка | ≤ 0.1 | 0.1–0.25 | > 0.25 |

Пороги не менялись с момента, когда INP заменил FID в марте 2024 ([web.dev через evelan.de](https://evelan.de/en/blog/core-web-vitals-optimize)). В интернете встречаются статьи про «LCP ужесточили до 2.0 с» — официально это не так, ориентируйся на web.dev.

### Важная деталь: 75-й перцентиль

Оценка считается не по среднему, а по **75-му перцентилю (p75)** реальных визитов. Это значит: страница «зелёная», только если **3 из 4 пользователей** получили хорошее значение. Мобилки и десктоп оцениваются отдельно.

Зачем это senior-у: если у тебя быстрый MacBook и офисный Wi‑Fi — ты видишь лучшие 10%. А p75 обычно определяют пользователи на среднем Android и мобильной сети.

### Страница проходит CWV, только если все три метрики зелёные

Если хоть одна метрика в «poor» или «needs improvement», страница в целом не проходит оценку. Поэтому нельзя «вытянуть» плохой CLS хорошим LCP.

## 2. Как измерять: lab vs field

Это первое, что должен понимать senior: **есть два типа данных, и они часто не совпадают**.

- **Field data (полевые, RUM)** — данные от реальных пользователей. Именно по ним Google ранжирует. Источник Google — **CrUX** (Chrome User Experience Report): анонимные данные из Chrome за последние 28 дней.
- **Lab data (лабораторные)** — один прогон в контролируемых условиях (Lighthouse, DevTools). Удобно для отладки и CI, но это «синтетика», а не правда о пользователях.

Типичная ситуация: Lighthouse показывает 98 баллов, а в Search Console страница «poor». Причины: у реальных юзеров слабее устройства и сеть, они кликают по странице (а Lighthouse — нет), у них другие кеши, A/B-тесты, баннеры, залогиненное состояние.

**INP почти невозможно честно измерить в лабе**, потому что он про реальные взаимодействия. В лабе вместо него смотрят **TBT** (Total Blocking Time) — это прокси-метрика.

### Инструменты

| Инструмент | Тип данных | Для чего использовать |
| --- | --- | --- |
| PageSpeed Insights | Field (CrUX) + Lab | Быстро глянуть URL: сверху реальные данные, снизу Lighthouse |
| Search Console → Core Web Vitals | Field (CrUX) | Видеть группы страниц-проблем по всему сайту |
| CrUX Dashboard / CrUX API / BigQuery | Field | Историю и тренды, сравнение с конкурентами |
| Lighthouse (DevTools, CLI, CI) | Lab | Отладка, регрессии в CI |
| DevTools → Performance panel | Lab + живые метрики | Главный инструмент отладки: показывает LCP-элемент, сдвиги, long tasks, INP по твоим кликам |
| Библиотека `web-vitals` | Field (свой RUM) | Собирать метрики со своих пользователей с детализацией |
| Vercel Speed Insights, Sentry, Datadog RUM и т.п. | Field | Готовый RUM без своей инфраструктуры |

Важно знать про браузеры: CrUX — это только Chrome. LCP и INP долго были только в Chromium; с конца 2025 года они стали частью Baseline, то есть доступны и в других основных браузерах ([roastweb.com](https://roastweb.com/blog/core-web-vitals-explained-2026)). Но Google всё равно ранжирует по CrUX.

### Совет по DevTools

В Performance panel включай **CPU throttling 4x–6x** и сетевой троттлинг. Без этого на мощном ноутбуке ты не увидишь проблем, которые есть у p75 пользователей.

## 3. LCP — Largest Contentful Paint

**Что это:** время от начала навигации до момента, когда отрисовался **самый большой видимый элемент** в первом экране. Цель — ≤ 2.5 с на p75.

**Какие элементы могут быть LCP:** `<img>`, `<image>` внутри SVG, постер `<video>`, элемент с `background-image` через CSS, крупный блок текста (`<h1>`, `<p>`). В 70%+ случаев на реальных сайтах LCP — это картинка (hero-баннер, фото товара).

LCP-элемент может меняться по ходу загрузки: сначала заголовок, потом подгрузилась картинка побольше — теперь она LCP. Метрика фиксируется на первом взаимодействии пользователя (клик, скролл).

### Главная идея: разложи LCP на 4 фазы

Не гадай, а смотри, какая фаза «толстая». Библиотека `web-vitals/attribution` и DevTools показывают это прямо.

| Фаза | Что происходит | Ориентир от LCP | Если эта фаза большая — что править |
| --- | --- | --- | --- |
| **1. TTFB** | Ждём первый байт HTML от сервера | ~40% | Сервер, кеш, CDN, редиректы (см. ниже) |
| **2. Resource load delay** | HTML пришёл, но браузер ещё **не начал** качать LCP-картинку | < 10% | Браузер поздно узнал о картинке → preload, priority, убрать lazy, не грузить через JS |
| **3. Resource load duration** | Картинка качается | ~40% | Картинка слишком тяжёлая → сжать, AVIF/WebP, правильный размер, CDN |
| **4. Element render delay** | Картинка скачана, но **не отрисована** | < 10% | Блокирующие CSS/JS, элемент рендерится только после гидрации, A/B-скрипт прячет страницу |

Самая частая проблема на практике — **фаза 2 (load delay)**, а не тяжесть картинки. Браузер просто поздно узнаёт, что её надо качать.

### Что править: TTFB (фаза 1)

- Отдавать HTML из кеша/CDN: статическая генерация (SSG), ISR, кеширование fetch и страниц в Next.js.
- Убрать цепочки редиректов (`http → https → www → /ru/`). Каждый редирект — это лишний round trip.
- Не делать медленные запросы к БД/API последовательно (waterfall на сервере) — делать параллельно через `Promise.all`.
- Использовать стриминг: отдать «оболочку» страницы сразу, медленные части — через `<Suspense>`.
- Серверы/edge ближе к пользователю.

### Что править: load delay (фаза 2)

- **LCP-картинка должна быть в HTML**, а не появляться после выполнения JS (клиентский fetch, клиентский рендер карусели).
- **Никогда не ставь `loading="lazy"` на LCP-картинку.** Это частая ошибка: lazy откладывает загрузку.
- `fetchpriority="high"` на LCP-картинку. В Next.js: `<Image priority />` (в новых версиях — `preload` / `fetchPriority="high"`, смотри доку своей версии).
- Если картинка в CSS `background-image` — браузер узнает о ней поздно. Лучше переделать на `<img>` или добавить `<link rel="preload" as="image">`.
- `preconnect` к домену с картинками, если это сторонний CDN.

### Что править: load duration (фаза 3)

- Современные форматы: AVIF / WebP (`next/image` делает это сам).
- Правильный размер под экран: `srcset` + `sizes`. В `next/image` обязательно указывай `sizes`, иначе на мобилке может скачаться огромная картинка.
- Сжатие (quality 70–80 обычно не отличить глазами).
- Меньше конкуренции за сеть: не грузить в первом экране кучу других картинок и шрифтов с высоким приоритетом.

### Что править: render delay (фаза 4)

- Уменьшить render-blocking CSS: критический CSS инлайнить, остальное грузить позже. Тяжёлые глобальные CSS-файлы — зло.
- Синхронные скрипты в `<head>` блокируют рендер. Сторонние скрипты — через `next/script` со стратегией `afterInteractive` или `lazyOnload`.
- **A/B-тест и anti-flicker скрипты** (прячут страницу через `opacity: 0`, пока не загрузится эксперимент) — классический убийца LCP.
- Если LCP-элемент рендерится только на клиенте (`'use client'` + `useEffect` + `useState`), то он появится только после загрузки и выполнения JS. Рендери его на сервере.
- Текстовый LCP: шрифт с `font-display: block` может держать текст невидимым. Используй `next/font` (по умолчанию `swap`).

### Пример: hero-картинка в Next.js

```tsx
import Image from 'next/image';

export default function Hero() {
  return (
    <Image
      src="/hero.jpg"
      alt=""
      width={1200}
      height={600}
      priority                 // preload + высокий приоритет, без lazy
      sizes="(max-width: 768px) 100vw, 1200px"
    />
  );
}
```

## 4. INP — Interaction to Next Paint

**Что это:** сколько проходит от действия пользователя (клик, тап, нажатие клавиши) до момента, когда браузер **нарисовал следующий кадр** с реакцией на это действие. Цель — ≤ 200 мс на p75.

INP смотрит на **все взаимодействия за всё время жизни страницы** и берёт почти самое худшее (на страницах с большим числом взаимодействий выкидывает выбросы: примерно 1 худшее на каждые 50). Скролл и hover не считаются — только клики, тапы и клавиатура.

**Почему заменил FID:** FID мерил только задержку **первого** взаимодействия и только время до старта обработчика. INP честнее: он учитывает все клики и полное время до отрисовки. FID официально заменён INP в марте 2024 года.

INP — самая частая проблема у React-приложений, потому что React-приложения много работают в главном потоке.

### Главная идея: главный поток (main thread)

В браузере JS, вычисление стилей, layout и отрисовка идут в **одном главном потоке**. Пока там выполняется задача, браузер не может обработать клик и не может нарисовать кадр.

**Long task** — задача длиннее 50 мс. Чем больше long tasks, тем хуже INP.

### 3 фазы INP

| Фаза | Что происходит | Типичная причина | Что править |
| --- | --- | --- | --- |
| **1. Input delay** | Клик произошёл, но главный поток занят чем-то другим | Гидрация, сторонние скрипты, таймеры, аналитика, тяжёлый код на загрузке | Меньше JS на старте, разбивать длинные задачи, откладывать третьи стороны |
| **2. Processing time** | Выполняются твои обработчики событий | Тяжёлый `onClick`/`onChange`, большой ререндер React, синхронные вычисления | Делать меньше в обработчике, оптимизировать ререндеры, уступать поток |
| **3. Presentation delay** | Обработчики отработали, браузер считает стили, layout и рисует | Огромный DOM, сложный CSS, layout thrashing, рендер тысяч элементов | Уменьшить DOM, виртуализация, `content-visibility` |

### Что править: общие приёмы

- **Уступай главный поток (yield).** Сначала сделай визуальную реакцию, а тяжёлую работу — в следующей задаче:

```ts
async function handleClick() {
  setIsOpen(true);               // быстрая визуальная реакция
  await scheduler.yield?.()      // отдать поток браузеру, чтобы он нарисовал кадр
    ?? new Promise(r => setTimeout(r, 0));
  sendAnalytics();               // тяжёлое и неважное — потом
}
```

- **Не делай тяжёлых синхронных вычислений в обработчике.** Фильтрация 10 000 элементов, парсинг JSON, сортировки — мемоизировать, делать заранее или вынести в Web Worker.
- **Аналитику и логирование — вне критического пути.** Отправка событий в обработчике клика часто занимает удивительно много времени.
- **Избегай layout thrashing:** не читай `offsetHeight`/`getBoundingClientRect` сразу после записи стилей в цикле.
- **Уменьшай размер DOM.** Больше ~1500 узлов — уже повод задуматься. Длинные списки — виртуализация (`@tanstack/react-virtual`, `react-window`).
- **`content-visibility: auto`** для больших блоков ниже первого экрана — браузер не рендерит их, пока они не видны.

### Что править: React-специфика

- **`useTransition` / `startTransition`** — пометить тяжёлое обновление как не срочное. React сначала отрисует срочное (например, ввод в инпут), а тяжёлый список обновит, когда будет время, и прервёт работу при новом вводе.
- **`useDeferredValue`** — то же самое для значения: инпут обновляется сразу, а тяжёлый список — с отложенным значением.

```tsx
const [query, setQuery] = useState('');
const deferredQuery = useDeferredValue(query);

return (
  <>
    <input value={query} onChange={e => setQuery(e.target.value)} />
    <HeavyList query={deferredQuery} />  {/* обёрнут в memo */}
  </>
);
```

- **Уменьшай область ререндера:** состояние держи как можно ниже по дереву; не клади часто меняющееся значение в контекст, на который подписано всё приложение. Используй селекторы в стейт-менеджерах (Zustand, Redux) вместо подписки на весь стор.
- **`memo`, `useMemo`, `useCallback`** — там, где профайлер показывает лишние ререндеры. React Compiler (если подключён) делает это автоматически.
- **Гидрация** — главный источник input delay в Next.js. Пока гидрируется большое дерево, клики ждут. Решение: меньше клиентских компонентов (см. раздел про Next.js), Suspense-границы (React гидрирует их по частям и в первую очередь ту часть, по которой кликнули).
- **Не используй контролируемые инпуты с тяжёлым ререндером на каждый символ.** Либо дебаунс, либо `useDeferredValue`, либо неконтролируемый инпут.

### Как найти виновника

1. DevTools → Performance → запиши, покликай по странице с CPU throttling 4x.
2. Найди взаимодействие на треке Interactions и посмотри, какая фаза длинная.
3. React DevTools Profiler → «Highlight updates» и запись коммита: кто ререндерится и сколько.
4. В проде — `web-vitals/attribution` + **LoAF** (Long Animation Frames API): показывает, какой скрипт и какая функция заняли кадр.

## 5. CLS — Cumulative Layout Shift

**Что это:** насколько сильно **неожиданно** сдвигаются видимые элементы на странице. Классика: хочешь нажать «Отмена», сверху подгрузился баннер — и ты нажал «Купить». Цель — ≤ 0.1 на p75. Это безразмерное число, не секунды.

### Как считается (на пальцах)

Один сдвиг = **impact fraction × distance fraction**:

- impact fraction — какую долю экрана затронули сдвинувшиеся элементы;
- distance fraction — на какую долю экрана они сдвинулись.

Пример: блок занимает половину экрана и сдвинулся на 1/4 экрана → область 0.75 (половина + путь), сдвиг 0.25 → 0.75 × 0.25 ≈ 0.19. Это уже «needs improvement» от одного сдвига.

**Session windows:** сдвиги группируются в «окна» (сдвиги с паузами < 1 с, окно не длиннее 5 с). CLS = сумма сдвигов в **самом плохом окне**. Поэтому долгоживущие SPA не накапливают CLS бесконечно.

**Что НЕ считается сдвигом:** изменения в течение 500 мс после клика/тапа/нажатия клавиши (пользователь сам вызвал, это ожидаемо). А вот скролл и hover — не считаются «ожиданием», сдвиги после них засчитываются.

Важно: CLS считается **за всю жизнь страницы**, не только при загрузке. Lighthouse видит только загрузку, поэтому в лабе CLS часто лучше, чем в поле.

### Причины и что править

| Причина | Что происходит | Как править |
| --- | --- | --- |
| Картинки/видео без размеров | Браузер не знает высоту, пока не скачал | `width`/`height` или CSS `aspect-ratio`. `next/image` требует размеры или `fill` с родителем фиксированного размера |
| Реклама, embed, iframe | Слот подгружается и раздвигает контент | Зарезервировать место: `min-height` под самый частый размер слота |
| Контент, вставляемый через JS сверху | Баннеры cookies, промо-плашки, «скачайте приложение» | Не вставлять над существующим контентом; использовать оверлей (`position: fixed`) или резервировать место |
| Веб-шрифты | Фоллбэк-шрифт другого размера → текст «перепрыгивает» при подмене | `next/font`: сам подбирает `size-adjust` для фоллбэка, хостит шрифт локально |
| Клиентская загрузка данных | Скелетон высотой 20px, а пришёл блок 400px | Скелетоны того же размера, что и контент |
| Различие SSR и клиента | На сервере рендерится одно, после гидрации — другое (например, по `window.innerWidth`) | Адаптивность через CSS media queries, а не через JS; одинаковый первый рендер |
| Анимации через `top`/`left`/`height` | Двигают layout | Анимировать только `transform` и `opacity` — они не вызывают сдвигов |

### Next.js / SPA особенности

- **bfcache** (back/forward cache): если страница восстанавливается из bfcache, она появляется мгновенно и без сдвигов. Не ломай его: не используй `unload`, не ставь `Cache-Control: no-store` без нужды.
- `loading.tsx` и Suspense-фоллбэки должны быть того же размера, что и итоговый контент.
- Блоки «зависящие от авторизации» (шапка с аватаром) — резервировать место, пока сессия неизвестна.

### Как найти виновника

- DevTools → Performance → трек **Layout shifts**: показывает, какой элемент сдвинулся.
- `web-vitals/attribution` в проде: даёт селектор элемента с самым большим сдвигом (`largestShiftTarget`).

## 6. Вспомогательные метрики

Они не входят в Core Web Vitals и напрямую на ранжирование не влияют, но помогают **найти причину** плохих CWV. Думай о них как о «диагностике».

| Метрика | Что измеряет | Good | На что влияет / зачем смотреть |
| --- | --- | --- | --- |
| **TTFB** (Time to First Byte) | Время до первого байта HTML (включая DNS, TLS, редиректы, сервер) | ≤ 0.8 с | Первая фаза LCP. Плохой TTFB = плохой LCP почти гарантированно |
| **FCP** (First Contentful Paint) | Когда отрисовался **первый** любой контент (текст, картинка) | ≤ 1.8 с | Если FCP плохой — проблема в TTFB или render-blocking ресурсах. Если FCP хороший, а LCP плохой — проблема конкретно в LCP-элементе |
| **TBT** (Total Blocking Time) | Сумма «лишнего» времени long tasks (всё, что > 50 мс) между FCP и TTI | ≤ 200 мс (лаб) | Лабораторный прокси для INP. Высокий TBT → скорее всего плохой INP |
| **Speed Index** | Как быстро визуально заполняется экран | ≤ 3.4 с (лаб) | Только Lighthouse, для общей картины |
| **FID** (First Input Delay) | Задержка первого взаимодействия | — | **Устарела**, заменена INP в 2024. Если видишь в старых дашбордах — переходи на INP |

### Lighthouse Performance Score

Это не CWV, а взвешенная оценка лабораторных метрик (TBT, LCP, CLS, FCP, Speed Index). Цифра «95 баллов» хороша для CI и регрессий, но **не равна прохождению CWV**. Бизнесу и SEO важны полевые p75, а не скор Lighthouse.

### Long Animation Frames (LoAF)

Новый браузерный API (замена Long Tasks API). Показывает кадры дольше 50 мс и **какие скрипты** в них выполнялись: URL файла, функцию, тип вызова. Это главный инструмент для поиска причин плохого INP в проде. Библиотека `web-vitals/attribution` уже использует LoAF и отдаёт эти данные в INP-атрибуции.

## 7. Мониторинг в продакшене

CrUX даёт данные с задержкой (окно 28 дней) и без деталей «почему». Senior должен настроить **свой RUM** (Real User Monitoring): собирать метрики с реальных пользователей с атрибуцией — какой элемент, какой скрипт, какая фаза.

### Вариант 1: `useReportWebVitals` в Next.js

```tsx
// app/_components/web-vitals.tsx
'use client';
import { useReportWebVitals } from 'next/web-vitals';

export function WebVitals() {
  useReportWebVitals((metric) => {
    const body = JSON.stringify({
      name: metric.name,        // LCP, INP, CLS, FCP, TTFB
      value: metric.value,
      rating: metric.rating,    // good | needs-improvement | poor
      id: metric.id,
      page: location.pathname,
    });
    // sendBeacon не теряет данные при закрытии вкладки
    navigator.sendBeacon?.('/api/vitals', body) ||
      fetch('/api/vitals', { body, method: 'POST', keepalive: true });
  });
  return null;
}
```

Подключается один раз в `app/layout.tsx`.

### Вариант 2: библиотека `web-vitals` с атрибуцией

Для диагностики нужна сборка `web-vitals/attribution` — она отдаёт причины:

```ts
import { onLCP, onINP, onCLS } from 'web-vitals/attribution';

onLCP(({ value, attribution }) => {
  // attribution.target — селектор LCP-элемента
  // attribution.timeToFirstByte, resourceLoadDelay,
  // resourceLoadDuration, elementRenderDelay — 4 фазы
});

onINP(({ value, attribution }) => {
  // attribution.interactionTarget — по чему кликнули
  // inputDelay, processingDuration, presentationDelay — 3 фазы
  // longAnimationFrameEntries — какие скрипты виноваты (LoAF)
});

onCLS(({ value, attribution }) => {
  // attribution.largestShiftTarget — что сдвинулось
});
```

### Что важно при сборе

- **Агрегируй по p75**, а не по среднему — так же, как Google.
- **Разделяй по типу устройства** (mobile/desktop), по **шаблону страницы** (route: `/product/[id]`, а не каждый URL) и по типу соединения.
- **Отправляй метрики через `sendBeacon`** или `fetch` с `keepalive` — INP и CLS финализируются, когда страница уходит в фон.
- **Учитывай soft navigations:** в SPA-переходах (клиентский роутинг Next.js) классические LCP/CLS считаются только для первой загрузки страницы. INP и CLS копятся на всю сессию до ухода со страницы. Это нормально, но учитывай при анализе.
- Готовые решения: Vercel Speed Insights, Sentry Performance, Datadog RUM, SpeedCurve, DebugBear. Свой вариант — эндпоинт + ClickHouse/BigQuery + дашборд.

### Performance budgets и CI

- **Lighthouse CI** в пайплайне: падать, если TBT, LCP или CLS хуже порога на ключевых страницах.
- **Бюджет на размер бандла:** `@next/bundle-analyzer` для анализа, `size-limit` или проверка в CI на JS первой загрузки.
- **Цели с запасом:** ставь внутренние цели строже порогов Google, например LCP < 2.0 с, INP < 150 мс, CLS < 0.05, и алерты при приближении к порогу ([digitalapplied.com](https://www.digitalapplied.com/blog/core-web-vitals-2026-inp-lcp-cls-optimization-guide)).
- **Алерты на регрессии в RUM** после каждого релиза — лаб в CI ловит не всё.

## 8. React / Next.js: что влияет на метрики

Главное правило: **чем меньше JS уходит в браузер и чем раньше пользователь получает HTML, тем лучше все три метрики**.

### Server Components (App Router)

- Серверные компоненты **не отправляют свой JS в браузер** и не гидрируются. Меньше JS → меньше гидрация → лучше INP и render delay в LCP.
- `'use client'` ставь **как можно ниже по дереву**: не на всю страницу, а на кнопку/форму/виджет. Ошибка: `'use client'` в `layout.tsx` или в корневом компоненте страницы — всё дерево под ним становится клиентским.
- Тяжёлые библиотеки (markdown-парсеры, форматирование дат, подсветка кода) используй в серверных компонентах — они не попадут в бандл.

### Стриминг и Suspense

- Оборачивай медленные части в `<Suspense>` (или используй `loading.tsx`): HTML с быстрой частью уходит сразу → лучше TTFB/FCP, а LCP-элемент не ждёт медленный API.
- **Но:** LCP-элемент не должен быть внутри медленной Suspense-границы, иначе он появится только когда придут данные.
- Suspense-границы позволяют React **гидрировать по частям** (selective hydration) и в приоритете гидрировать ту часть, по которой кликнули → лучше INP.

### Загрузка данных

- Избегай waterfall-запросов: параллельно через `Promise.all`, начинай запросы как можно выше по дереву.
- Кеширование и статика: SSG/ISR, кеш `fetch`, `revalidate`, кеш-директивы (в новых версиях Next.js — `'use cache'`). Кешированная страница из CDN = маленький TTFB.
- Клиентский fetch для контента первого экрана — плохо для LCP: контент появится только после JS + запроса. Данные для первого экрана получай на сервере.

### Code splitting

- `next/dynamic` для тяжёлых компонентов, которые не нужны сразу: модалки, графики, редакторы, карты.

```tsx
import dynamic from 'next/dynamic';
const Chart = dynamic(() => import('./Chart'), {
  ssr: false, // в App Router — только внутри 'use client' компонента
  loading: () => <div style={{ height: 300 }} />, // резерв места против CLS
});
```

- Импортируй точечно: `import debounce from 'lodash/debounce'`, а не весь lodash. Проверяй бандл через `@next/bundle-analyzer`.
- Следи за «бочками» (barrel files, `index.ts` с реэкспортом всего) — они могут тянуть лишнее. В Next.js есть `optimizePackageImports`.

### Встроенные компоненты Next.js

| Компонент | Какая метрика | Что даёт |
| --- | --- | --- |
| `next/image` | LCP, CLS | Форматы AVIF/WebP, `srcset`, lazy по умолчанию, `priority` для LCP, обязательные размеры против CLS |
| `next/font` | CLS, LCP | Self-hosting шрифтов (без запроса к Google Fonts), `size-adjust` фоллбэка, `display: swap` |
| `next/script` | INP, LCP | Стратегии `beforeInteractive` / `afterInteractive` / `lazyOnload` / `worker` для сторонних скриптов |
| `next/link` | Навигации | Префетч страниц в зоне видимости → мгновенные переходы |

### Сторонние скрипты

Аналитика, чаты поддержки, пиксели рекламы, A/B-тесты, тег-менеджеры часто дают **больше половины проблем с INP**.

- Проведи аудит: что реально нужно, что можно удалить.
- Грузи через `next/script` с `lazyOnload` всё, что не критично.
- Чат поддержки — подгружать по клику на «фасад» (картинка-кнопка), а не на старте.
- Partytown (`strategy="worker"`) — выносит скрипты в Web Worker, но экспериментально, проверяй совместимость.

### Гидрация и ошибки гидрации

- Hydration mismatch заставляет React перерендерить часть дерева на клиенте → лишняя работа (хуже INP) и возможные сдвиги (хуже CLS). Исправляй все предупреждения о гидрации.
- Не рендери разное на сервере и клиенте через `typeof window`. Для клиент-онли контента — `useEffect` или `dynamic(..., { ssr: false })` с резервом места.

## 9. Senior-уровень: контекст, мифы, процесс

### Влияние на SEO — честно

- CWV — **подтверждённый сигнал ранжирования**, но не главный. Релевантный контент важнее. CWV работают скорее как «тай-брейкер» между похожими по качеству страницами.
- Google берёт данные из CrUX. Если у страницы мало трафика, данных по ней нет — тогда используется оценка по группе похожих страниц или по всему origin.
- Улучшения видны в Search Console только через ~28 дней (окно CrUX). Не жди эффекта на следующий день после релиза.

### Бизнес-аргументы

Для менеджмента CWV важны не из-за SEO, а из-за **конверсии**: быстрее загрузка и отзывчивость → меньше отказов, выше конверсия. Лучший аргумент — свои данные: свяжи RUM-метрики с бизнес-метриками (конверсия, отказы) по сегментам «быстрые vs медленные сессии». Кейсы других компаний можно найти на [web.dev в разделе Case studies](https://web.dev/case-studies/).

### Частые мифы и ошибки

| Миф / ошибка | Как на самом деле |
| --- | --- |
| «У нас Lighthouse 95, значит всё ок» | Ранжирование и UX — по полевым данным p75. Лаб ≠ поле |
| «Проверил на своём MacBook — быстро» | Тестируй с CPU throttling и на реальном среднем Android |
| «Поставим lazy на все картинки» | Lazy на LCP-картинке ухудшает LCP |
| «Обернём всё в `useMemo` и `memo`» | Мемоизация без профилирования — шум. Сначала Profiler, потом точечные фиксы |
| «SPA-переходы улучшат LCP» | Классический LCP считается только на первой (hard) загрузке. Переходы улучшают UX, но не этот LCP |
| «CLS — это только при загрузке» | CLS считается за всю жизнь страницы, включая скролл и ленивую подгрузку |
| «Средние значения в норме» | Важен p75 и хвост; среднее прячет медленных пользователей |
| «Пофиксили — забыли» | Без мониторинга и бюджетов метрики деградируют с каждым релизом |

### Как вести работу над перфомансом в команде

1. **Измерь** — настрой RUM с атрибуцией, сегментацию по шаблонам страниц и устройствам.
2. **Приоритизируй** — начни с шаблонов с наибольшим трафиком и худшими p75 (листинг, карточка товара, главная). Чинить шаблон выгоднее, чем отдельные страницы.
3. **Найди фазу** — для LCP одну из 4 фаз, для INP одну из 3, для CLS конкретный элемент. Не чини вслепую.
4. **Исправь и проверь в лабе**, затем **подтверди в RUM** через 1–2 недели.
5. **Защити результат** — бюджеты в CI, алерты в RUM, правила в код-ревью (например: «новый сторонний скрипт — только через ревью перформанса»).
6. **Обучай команду** — короткие гайды: как правильно вставить картинку, когда `'use client'`, как подключать сторонние скрипты.

Типичный порядок по сложности: CLS обычно чинится быстрее всего (часто CSS), LCP — инфраструктура и картинки, INP — самый трудный, требует профилирования JS.

## 10. Чеклист для повторения

### Основы

- [ ] Три Core Web Vitals: **LCP ≤ 2.5 с**, **INP ≤ 200 мс**, **CLS ≤ 0.1**
- [ ] Оценка по **p75** реальных пользователей, отдельно mobile и desktop; должны пройти все три
- [ ] Field (CrUX, RUM) — правда для SEO и UX; lab (Lighthouse) — для отладки и CI
- [ ] INP заменил FID в марте 2024; в лабе вместо INP смотрим TBT

### LCP

- [ ] Знаю LCP-элемент каждого ключевого шаблона
- [ ] Разложил LCP на 4 фазы: TTFB → load delay → load duration → render delay
- [ ] LCP-картинка есть в исходном HTML, без `lazy`, с `priority` / `fetchpriority="high"`
- [ ] Картинки в AVIF/WebP, с `sizes`, правильного размера
- [ ] HTML из кеша/CDN (SSG/ISR), нет цепочек редиректов, нет waterfall-запросов на сервере
- [ ] Нет anti-flicker скриптов и блокирующего JS/CSS в `<head>`

### INP

- [ ] Знаю 3 фазы: input delay → processing → presentation delay
- [ ] Минимум `'use client'`, клиентские компоненты как можно ниже по дереву
- [ ] Тяжёлые обновления через `useTransition` / `useDeferredValue`
- [ ] В обработчиках: сначала визуальная реакция, потом `yield`, потом тяжёлая работа
- [ ] Нет лишних ререндеров (проверено в React Profiler), часто меняющееся состояние не в глобальном контексте
- [ ] Длинные списки виртуализированы, DOM небольшой
- [ ] Сторонние скрипты отложены (`lazyOnload`) или загружаются по клику

### CLS

- [ ] У всех картинок, видео, iframe есть размеры или `aspect-ratio`
- [ ] Место под рекламу, баннеры, динамические блоки зарезервировано
- [ ] Шрифты через `next/font`
- [ ] Скелетоны и `loading.tsx` того же размера, что контент
- [ ] Анимации только через `transform` / `opacity`
- [ ] Нет различий SSR и клиента (адаптив через CSS, нет hydration mismatch)

### Процесс

- [ ] RUM с атрибуцией (`web-vitals/attribution` или `useReportWebVitals`), агрегирую по p75 и шаблонам
- [ ] Lighthouse CI + бюджет на бандл в пайплайне
- [ ] Внутренние цели строже порогов Google (LCP < 2.0 с, INP < 150 мс, CLS < 0.05)
- [ ] Алерты на регрессии после релизов
- [ ] Порядок работы: измерить → найти фазу → исправить → проверить в лабе → подтвердить в поле → защитить бюджетом
