# Стратегии рендеринга фронтенда и Next.js: конспект

## 1. Базовые понятия

Любая стратегия рендеринга отвечает на три вопроса: **где** превращаем компоненты в HTML (сервер, CI на этапе сборки, браузер), **когда** (на build, на каждый запрос, по таймеру/событию) и **сколько JS** потом нужно браузеру, чтобы страница ожила.

**Рендеринг** — превращение дерева компонентов в HTML-строку (на сервере) или в DOM-узлы (в браузере).

**Гидратация** — React в браузере заново выполняет компоненты, сверяет результат с уже пришедшим HTML и навешивает обработчики событий. HTML не пересоздаётся, но **весь JS этих компонентов должен быть скачан и выполнен**. Отсюда главный вывод: «отрендерено на сервере» не значит «не попало в бандл».

**Бандл** — JS, который браузер скачивает. Делится на чанки: фреймворк (React, роутер), общий код, код конкретной страницы, лениво подгружаемые чанки.

**Payload данных** — данные, которые сервер передаёт клиенту для гидратации. В Pages Router это JSON в `<script id="__NEXT_DATA__">`, в App Router — RSC payload (поток `self.__next_f.push(...)` в HTML и `.rsc`/`?_rsc=` запросы при навигации).

**Метрики, на которые влияет выбор стратегии:**

| Метрика | Что измеряет | Что её портит |
| --- | --- | --- |
| TTFB | Время до первого байта ответа | Тяжёлый SSR, медленные запросы к БД на каждый запрос |
| FCP / LCP | Когда видно первое / главное содержимое | CSR (пустой HTML), блокирующий JS, поздняя загрузка данных |
| TBT / INP | Отзывчивость, блокировка главного потока | Большой бандл, долгая гидратация |
| CLS | Прыжки вёрстки | Контент, который подгружается на клиенте без зарезервированного места |
| SEO / шаринг | Видят ли боты и превью контент | Контент, которого нет в исходном HTML |

**Ключевая модель:** у каждой страницы есть «стоимость HTML» (кто и когда его делает) и «стоимость интерактивности» (сколько JS нужно гидратировать). Стратегии рендеринга двигают первую, React Server Components и острова — вторую.

## 2. Стратегии рендеринга

Все стратегии — это комбинации «где и когда строится HTML» и «сколько JS гидратируется». Ниже — каждая по схеме: как работает → что приходит браузеру → когда брать.

### 2.1 CSR — Client-Side Rendering

Сервер отдаёт почти пустой HTML (`<div id="root"></div>`) и JS-бандл. Браузер скачивает JS, запрашивает данные (fetch к API), рендерит DOM.

- **Приходит:** пустая оболочка + весь JS приложения; данные — отдельными запросами после загрузки JS.
- **Плюсы:** простая инфраструктура (статический хостинг/CDN), дешёвый сервер, богатая интерактивность, быстрые переходы после первой загрузки.
- **Минусы:** плохой LCP (водопад: HTML → JS → данные → рендер), SEO и превью ссылок зависят от выполнения JS, большой бандл.
- **Когда:** закрытые за логином дашборды, админки, редакторы, SaaS-приложения, где SEO не нужно.

### 2.2 SSR — Server-Side Rendering (на каждый запрос)

На каждый запрос сервер получает данные, рендерит HTML и отдаёт его вместе с данными для гидратации и JS.

- **Приходит:** полный HTML + данные (JSON/RSC payload) + JS для гидратации.
- **Плюсы:** актуальные и персональные данные (cookies, заголовки, гео), хорошее SEO, быстрый FCP.
- **Минусы:** TTFB зависит от самого медленного запроса данных, нагрузка на сервер, сложнее кэшировать на CDN; гидратация всё равно стоит JS.
- **Когда:** персонализированные страницы, поиск с фильтрами в URL, страницы, данные которых меняются каждую секунду и важны для SEO.

### 2.3 SSG — Static Site Generation

HTML генерируется один раз на этапе сборки (`next build`) и раздаётся с CDN как файл.

- **Приходит:** готовый HTML + данные для гидратации (тот же JSON/RSC payload, но сгенерированный при сборке) + JS.
- **Плюсы:** минимальный TTFB, дёшево, отказоустойчиво, отличное SEO.
- **Минусы:** данные устаревают до следующей сборки, долгие сборки при тысячах страниц, нет персонализации в HTML.
- **Когда:** лендинги, документация, блог, маркетинг, справочники.
- **Важно:** SSG не означает «без JS». Компоненты с хуками рендерятся при сборке в HTML со начальным состоянием (`useState(initial)`), а потом гидратируются. `useEffect` на сервере не выполняется.

### 2.4 ISR — Incremental Static Regeneration

SSG + фоновая перегенерация. Страница отдаётся из кэша; по истечении `revalidate` секунд первый пришедший получает старую версию, а сервер в фоне строит новую (stale-while-revalidate). Есть и on-demand ревалидация: `revalidatePath` / `revalidateTag` / `res.revalidate()` по вебхуку из CMS.

- **Приходит:** то же, что у SSG.
- **Плюсы:** скорость SSG + относительная свежесть, не надо пересобирать весь сайт, можно генерировать страницы по требованию.
- **Минусы:** нужен сервер (не работает в `output: 'export'`), кто-то увидит устаревшую версию, сложнее отладка кэша.
- **Когда:** каталоги товаров, новости, карточки, контент из CMS.

### 2.5 Streaming SSR

Сервер начинает отдавать HTML сразу (шапку, оболочку), а медленные части досылает в том же ответе по мере готовности. В React это `<Suspense>`: сначала приходит fallback, потом скрытый HTML-кусок + маленький скрипт, который ставит его на место. Плюс **селективная гидратация**: React гидратирует готовые куски независимо и в первую очередь тот, с которым взаимодействует пользователь.

- **Плюсы:** TTFB и FCP не ждут самый медленный запрос.
- **Минусы:** HTTP-статус и заголовки уходят до окончания рендера (ошибка внутри Suspense не превратит ответ в 500), нужно продумывать fallback-ы.
- **В Next.js:** App Router ([`loading.tsx` и `<Suspense>`](#67-стриминг-и-loadingtsx)). Pages Router стриминг не поддерживает.

### 2.6 Островная архитектура (Islands) и частичная гидратация

Страница — статический HTML, а интерактивные куски («острова») гидратируются по отдельности, часто лениво (при видимости, при idle). Код неинтерактивных частей в браузер **не попадает вообще**.

- **Где:** Astro (`client:load`, `client:visible`), Fresh, Eleventy + is-land.
- **Аналог в Next.js:** App Router: Server Components — «море», Client Components (`'use client'`) — «острова». Отличие: в Next навигация всё равно клиентская, и острова гидратируются вместе, без директив вида `client:visible`.

### 2.7 Resumability

Вместо гидратации фреймворк сериализует состояние и обработчики в HTML и подгружает код конкретного обработчика только при событии. Почти нулевой JS на старте. Пример — Qwik. Next.js так не делает, но полезно знать как противоположный полюс.

### 2.8 PPR — Partial Prerendering

Одна страница = статическая оболочка, сгенерированная при сборке (отдаётся с CDN мгновенно) + «динамические дыры» в `<Suspense>`, которые досылаются стримингом в **том же ответе**. Это и есть «большая часть SSG, маленькая часть SSR» на уровне фреймворка. В Next.js 16 PPR — основа модели Cache Components (флаг `cacheComponents: true`), отдельный `experimental.ppr` убран.

### 2.9 Edge-рендеринг

Не отдельная стратегия, а **место** выполнения SSR/middleware: на узлах CDN близко к пользователю. Меньше латентность, но ограниченный рантайм (нет части Node API), и если база данных в одном регионе — выигрыш съедается запросами к ней. Cache Components / `use cache` требуют Node-рантайма.

### 2.10 Prerender / SPA с пререндером, static export

`output: 'export'` в Next.js — чистый SSG без сервера: только HTML/CSS/JS-файлы. Не работает: ISR, SSR, middleware/proxy, Server Actions, кэш, `cookies()`. Подходит для хостинга на S3/GitHub Pages.

### Сводная таблица

| Стратегия | Когда строится HTML | Свежесть данных | TTFB | SEO | Нагрузка на сервер | Нужен сервер |
| --- | --- | --- | --- | --- | --- | --- |
| CSR | В браузере | Всегда свежие | Низкий, но контента нет | Слабо | Минимальная | Нет |
| SSR | На каждый запрос | Свежие, персональные | Высокий/средний | Отлично | Высокая | Да |
| Streaming SSR | На запрос, частями | Свежие | Низкий | Отлично | Высокая | Да |
| SSG | При сборке | До следующей сборки | Минимальный | Отлично | Нет | Нет |
| ISR | При сборке + в фоне | Задержка = revalidate | Минимальный | Отлично | Низкая | Да |
| PPR | Оболочка при сборке, дыры на запрос | Оболочка кэш, дыры свежие | Минимальный | Отлично | Средняя | Да |
| Islands | При сборке/запросе, JS точечно | Зависит | Низкий | Отлично | Низкая | Опционально |

## 3. Схема выбора стратегии

Стратегию выбирают **для каждой страницы (а в App Router — для каждого куска страницы)**, а не для всего проекта. Первый проход — четыре вопроса о HTML; второй — отдельный вопрос о том, сколько JS гидратировать.

[дерево выбора стратегии: 4 вопроса, 6 исходов]

Идите сверху вниз: если контент не нужен в HTML — CSR; общий для всех — выбор по частоте изменений; персональный — по тому, вся ли страница зависит от пользователя.

### Критерии и в какую сторону они толкают

| Критерий | Толкает к статике (SSG/ISR/PPR-оболочка) | Толкает к динамике (SSR/стриминг) | Толкает к клиенту (CSR/острова) |
| --- | --- | --- | --- |
| SEO и превью ссылок | Важны | Важны и данные свежие | Не важны (за логином) |
| Персонализация | Нет или в маленьком блоке | Вся страница зависит от cookies/сессии | Персональные данные не нужны в HTML |
| Частота изменений данных | При деплое, минуты–часы | Каждый запрос, секунды | Реалтайм после загрузки (WebSocket) |
| Число страниц | Сотни/тысячи — ISR + генерация по требованию | Бесконечно (поиск, фильтры) | Не важно |
| Требования к TTFB/LCP | Жёсткие — CDN | Допустимо ожидание данных | LCP не критичен |
| Стоимость инфраструктуры | Минимальная (CDN) | Сервер на каждый запрос | Статический хостинг |
| Где лежат данные | Доступны при сборке | Только в момент запроса (cookies, гео) | Только в браузере (localStorage, геолокация) |
| Интерактивность | Мало → Server Components | — | Много → Client Components |

### Второй проход: сколько JS

- По умолчанию — Server Components; `'use client'` только на интерактивных листьях (кнопки, формы, вкладки).
- Код, который трогает `window` при импорте или не нужен для SEO и первого экрана, — `dynamic(..., { ssr: false })`.
- Тяжёлое, но редкое (модалки, редакторы) — [`next/dynamic`](#8-nextdynamic-ssr-truefalse-и-типичные-ловушки) по условию.
- Реалтайм-обновления (чат, котировки) — Client Component поверх серверного первого рендера.

### Правила при сомнениях

1. Начинайте со статики и уходите в динамику только ради конкретного требования.
2. Если динамика нужна в одном блоке — не делайте динамической всю страницу ([раздел 4](#4-комбинации-стратегий-на-одной-странице)).
3. Не путайте свежесть с динамикой: «обновляется раз в 5 минут» — это ISR, а не SSR.

## 4. Комбинации стратегий на одной странице

Главный вопрос комбинаций — **гранулярность**: на каком уровне фреймворк позволяет выбирать стратегию. Pages Router — одна стратегия на страницу; App Router до Cache Components — на маршрут (сегмент) с кэшем на уровне fetch; App Router с Cache Components (Next.js 16) — на уровне компонента.

| Окружение | Гранулярность | Как сделать «почти всё SSG, кусок динамики» |
| --- | --- | --- |
| Pages Router | Страница: либо `getStaticProps`, либо `getServerSideProps` | SSG/ISR-страница + динамика через клиентский fetch или `dynamic(..., { ssr: false })` |
| App Router (Next 13–15, без PPR) | Маршрут: одно `cookies()` делает весь маршрут динамическим | Вынести динамику в Client Component с fetch на клиенте или в отдельный route handler |
| App Router + Cache Components (Next 16) | Компонент: статическая оболочка + дыры в `<Suspense>` | PPR из коробки: динамика в Suspense, кэшируемое — `'use cache'` |

### Паттерн A: статическая страница + клиентский островок (работает везде)

Страница — SSG/ISR, общая для всех. Персональный кусок (корзина, «Привет, Иван», избранное) — Client Component, который после гидратации делает запрос к API (SWR / TanStack Query).

- **В HTML:** контент + скелетон на месте персонального блока.
- **Цена:** дополнительный запрос после загрузки JS, мелькание скелетона, CLS если не зарезервировать место.
- **Когда:** персональные данные не нужны для SEO, а страница должна оставаться кэшируемой на CDN.

### Паттерн B: PPR — статическая оболочка + серверные дыры (Next.js 16)

```tsx
// next.config.ts → cacheComponents: true
export default function ProductPage({ params }) {
  return (
    <>
      <ProductInfo params={params} />   {/* 'use cache' → в статической оболочке */}
      <Suspense fallback={<CartSkeleton />}>
        <Cart />                         {/* читает cookies() → дыра, рендер на запрос */}
      </Suspense>
    </>
  )
}
```

- **В ответе:** сначала с CDN мгновенно уходит оболочка с фолбэками, затем в **том же HTTP-ответе** досылается HTML корзины + её RSC payload.
- **Отличие от паттерна A:** нет второго круга «загрузился JS → пошёл fetch», данные подтягиваются на сервере, рядом с БД, а Server Component корзины не добавляет JS.
- Правило [Cache Components](#66-cache-components-nextjs-16): всё, что читает рантайм-данные (`cookies()`, `headers()`, `searchParams`, некэшированный fetch) и не обёрнуто в `<Suspense>`, — ошибка сборки. Это заставляет явно размечать границу «статика/динамика».

### Паттерн C: streaming SSR с Suspense

Вся страница динамическая, но медленные куски обёрнуты в `<Suspense>`. От PPR отличается тем, что оболочка тоже рендерится на каждый запрос (не с CDN). Хорошо для страниц, где почти всё персональное.

### Паттерн D: персонализация через middleware/proxy + статические варианты

Заранее генерируются варианты страницы (локали, A/B-ветки, регионы) как SSG. `middleware.ts` (в Next 16 — `proxy.ts`) смотрит cookie/гео и делает rewrite на нужный вариант. Персонализация без SSR, всё отдаётся с CDN. Годится, когда вариантов мало.

### Паттерн E: разная свежесть внутри статики

В App Router у каждого fetch/кэшируемой функции своя `revalidate`/`cacheLife`. Например, описание товара — `cacheLife('days')`, цена — `cacheLife('minutes')`. Без Cache Components действует правило: у маршрута итоговое `revalidate` = минимальное из всех fetch и сегментов.

### Паттерн F: статическая страница + мутации

Страница SSG/ISR, а изменения (форма, лайк, отзыв) — через Server Action или API-роут, после которых вызывается `revalidatePath`/`revalidateTag` (или `updateTag` в Next 16, если пользователь должен сразу увидеть свои изменения).

### Паттерн G: SSR/SSG-страница + клиент-онли компонент

Карты, графики, редакторы, всё, что трогает `window` при импорте, — через `dynamic(() => import('./Map'), { ssr: false })`. Остальная страница рендерится на сервере, на месте компонента в HTML — только `loading`. Подробно — в [разделе 8](#8-nextdynamic-ssr-truefalse-и-типичные-ловушки).

### Как не «отравить» статическую страницу

- Одно обращение к `cookies()`/`headers()` в layout делает динамическим **каждый** маршрут под ним (без Cache Components).
- `fetch(..., { cache: 'no-store' })` или `export const dynamic = 'force-dynamic'` — то же самое.
- Чтение `searchParams` в странице — динамика. Если параметр нужен только клиенту, читайте его в Client Component через `useSearchParams()` внутри `<Suspense>`.
- Проверка: вывод `next build` показывает значок у каждого маршрута (○ static, ● SSG с generateStaticParams/getStaticProps, ƒ dynamic, ◐ partial prerender).

## 5. Next.js Pages Router

В Pages Router твоя интуиция верна: **каждый компонент страницы рендерится на сервере в HTML (при сборке или на запрос), а затем весь его JS скачивается и гидратируется в браузере** — в том числе компоненты без хуков и без интерактивности. Понятия Server Component здесь нет: в терминах App Router всё в Pages Router — «клиентские компоненты, которые ещё и SSR-ятся».

### 5.1 Функции данных и стратегии

| Что экспортирует страница | Стратегия | Когда выполняется |
| --- | --- | --- |
| Ничего (нет функций данных) | Automatic Static Optimization: SSG без данных | HTML при `next build` |
| `getStaticProps` | SSG | При сборке (в dev — на каждый запрос) |
| `getStaticProps` + `revalidate: N` | ISR | При сборке + в фоне не чаще раза в N с |
| `getStaticPaths` + `getStaticProps` | SSG динамических путей `[slug]` | При сборке для перечисленных путей, остальные — по `fallback` |
| `getServerSideProps` | SSR | На каждый запрос |
| `getInitialProps` (устаревшее) | SSR | Первый запрос — сервер; клиентская навигация — **в браузере** (код попадает в бандл) |

Одна страница = одна стратегия: нельзя совместить `getStaticProps` и `getServerSideProps`. Динамику внутри SSG-страницы делают только на клиенте ([раздел 4](#4-комбинации-стратегий-на-одной-странице), паттерн A).

### 5.2 Что приходит при первом запросе

```html
<html>
  <body>
    <div id="__next">…полный HTML страницы…</div>
    <script id="__NEXT_DATA__" type="application/json">
      {"props":{"pageProps":{…}},"page":"/blog/[slug]","query":{…},"buildId":"…","isFallback":false}
    </script>
    <script src="/_next/static/chunks/webpack-….js"></script>
    <script src="/_next/static/chunks/framework-….js"></script>   <!-- React, ReactDOM -->
    <script src="/_next/static/chunks/main-….js"></script>        <!-- роутер Next -->
    <script src="/_next/static/chunks/pages/_app-….js"></script>
    <script src="/_next/static/chunks/pages/blog/[slug]-….js"></script>
  </body>
</html>
```

1. **HTML** — полная разметка всех компонентов, включая клиентские с хуками (в начальном состоянии).
2. **`__NEXT_DATA__`** — props из `getStaticProps`/`getServerSideProps`, сериализованные в JSON. Они нужны, чтобы при гидратации React получил тот же результат, что и на сервере. Всё, что вернёте в props, — **в HTML и видно всем**, поэтому не возвращайте лишние поля (раздувают HTML и утечка данных).
3. **JS** — код **всех** компонентов страницы + `_app`. Не попадают в бандл: `getStaticProps`, `getServerSideProps`, `getStaticPaths` и модули, импортированные только ими (Next вырезает их на этапе компиляции), а также `_document` и API-роуты.

### 5.3 Клиентская навигация (next/link)

При переходе HTML не запрашивается. Next скачивает JS-чанк страницы (обычно уже предзагружен при появлении ссылки во viewport) и JSON с props: `/_next/data/<buildId>/blog/hello.json`. Для SSG этот JSON — статический файл; для `getServerSideProps` — **запрос на сервер при каждом переходе**.

### 5.4 Что происходит с хуками при SSG/SSR

- `useState(initial)` — на сервере рендерится с `initial`, в HTML попадает это значение.
- `useEffect` / `useLayoutEffect` — на сервере не выполняются; срабатывают после гидратации. Поэтому fetch в `useEffect` = данные **не попадут** в HTML.
- `useRouter().query` на статической странице без `getStaticProps`/`getServerSideProps` при первом рендере пуст (`router.isReady === false`), заполняется после гидратации.
- Код, который на верхнем уровне компонента читает `window`, `localStorage`, `Date.now()`, `Math.random()`, даёт разный результат на сервере и клиенте → **hydration mismatch**.

### 5.5 getStaticPaths и fallback

| `fallback` | Неизвестный путь при запросе | Что видит пользователь | Когда использовать |
| --- | --- | --- | --- |
| `false` | 404 | 404 | Все пути известны при сборке, их немного |
| `true` | Сразу отдаётся «фолбэк-версия» страницы, генерация идёт в фоне | Сначала `router.isFallback === true` и пустые props (нужен скелетон), потом подгружается JSON и страница перерисовывается; следующие запросы получают готовый HTML | Очень много страниц, важна мгновенная отдача |
| `'blocking'` | Сервер рендерит страницу как SSR и ждёт | Сразу готовый HTML (без скелетона); результат кэшируется как статический | Много страниц, важно SEO и нет желания делать фолбэк-UI |

Нюанс `fallback: true`: компонент должен уметь рендериться без props (`if (router.isFallback) return <Skeleton/>`). Для поисковых ботов Next обычно отдаёт уже отрендеренную страницу, как при `'blocking'`. В App Router аналог — `dynamicParams` (`true` ≈ blocking, `false` ≈ 404).

### 5.6 Оптимизация бандла в Pages Router

- Тяжёлую обработку (парсинг markdown, форматирование, фильтрация) переносите в `getStaticProps`: тогда библиотека остаётся на сервере, в клиент уходят только готовые данные.
- Тяжёлые редко используемые компоненты — через `next/dynamic` (выносятся в отдельный чанк).
- Анализ — `@next/bundle-analyzer`.

## 6. Next.js App Router

Короткий ответ на главный вопрос: **в App Router Client Components (`'use client'`) тоже рендерятся на сервере в HTML (при сборке или на запрос) и потом гидратируются — ровно как в Pages Router.** Новое — Server Components: они тоже дают HTML, но их JS **никогда не попадает в браузер** и они не гидратируются. `'use client'` значит «этот компонент нужен ещё и в браузере», а не «рендерить только в браузере».

### 6.1 Два вида компонентов

|  | Server Component (по умолчанию) | Client Component (`'use client'`) |
| --- | --- | --- |
| Где выполняется | Только на сервере (при сборке или на запрос) | На сервере (пререндер в HTML) **и** в браузере |
| Есть ли в HTML первого запроса | Да | Да (с начальным состоянием) |
| JS в бандле | Нет | Да |
| Гидратация | Нет | Да |
| Хуки состояния/эффекты, обработчики событий, `window` | Нельзя | Можно |
| async/await, доступ к БД, секреты, fs | Можно | Нельзя (секреты утекут) |
| Как попадает в браузер | Как готовый результат в RSC payload | Как ссылка на модуль в payload + JS-чанк |

### 6.2 Граница `'use client'`

- Директива ставит **границу**: файл с ней и всё, что он импортирует, попадает в клиентский граф модулей и в бандл.
- Server Component может импортировать и рендерить Client Component. Client Component **не может импортировать** Server Component — но может получить его как `children` или проп (композиция). Тогда серверная часть останется серверной:

```tsx
// layout.tsx (server)
<ClientTabs>            {/* клиентский, в бандле */}
  <ServerArticle />     {/* серверный, в бандл не попадёт, приходит готовым в payload */}
</ClientTabs>
```

- Пропсы, передаваемые с сервера в Client Component, должны сериализоваться (JSON + Date, Map, Set, Promise, JSX). Функции нельзя, кроме Server Actions. Все эти пропсы оказываются в RSC payload внутри HTML — то же правило «не передавать лишнего», что и с `__NEXT_DATA__`.
- Ставьте `'use client'` как можно ниже по дереву (на кнопке, а не на всей странице) — это напрямую уменьшает бандл.
- Пакеты `server-only` / `client-only` превращают случайный импорт не в ту среду в ошибку сборки.

### 6.3 Конвейер первого запроса

1. **RSC-рендер.** Сервер выполняет Server Components (с await данных). Результат — RSC payload: сериализованное дерево, где серверные компоненты уже «развёрнуты» в обычные элементы (`div`, текст), а на месте клиентских стоят ссылки «модуль X из чанка Y, вот его пропсы».
2. **SSR в HTML.** Из payload + кода клиентских компонентов React рендерит HTML. Здесь клиентские компоненты выполняются на сервере с начальным состоянием.
3. **Отправка.** В ответе: HTML, тот же payload, встроенный строками `self.__next_f.push([1,"…"])`, и `<script>` только для чанков **клиентских** компонентов этого маршрута + рантайма React/роутера.
4. **В браузере.** HTML показан сразу. React читает payload, восстанавливает дерево и гидратирует только клиентские компоненты. Серверные части просто «принимаются» как есть.

Побочный эффект: текст серверных компонентов приходит **дважды** — в HTML и в payload. Это цена за то, что клиентский роутер может обновлять дерево без перезагрузки. Крупный статический контент всё равно обычно дешевле, чем JS, который бы его рендерил.

### 6.4 Клиентская навигация

`<Link>` запрашивает не HTML и не JSON-props, а **RSC payload** нового маршрута (запрос с заголовком `RSC: 1` / параметром `?_rsc=`). Приходят только изменившиеся сегменты: общие layout не перерендериваются и сохраняют состояние. Плюс докачиваются JS-чанки новых клиентских компонентов, если их ещё нет. Payload хранится в клиентском Router Cache; ссылки во viewport предзагружаются (для динамических маршрутов — до ближайшего `loading.tsx`).

### 6.5 Статический и динамический рендеринг (Next.js 13–15, без Cache Components)

Маршрут **статический по умолчанию** и пререндерится при `next build` в HTML + `.rsc`-файл (Full Route Cache). Он становится **динамическим** (рендер на каждый запрос), если где-то в дереве:

- вызывается `cookies()`, `headers()`, `connection()`, `draftMode()`;
- читаются `searchParams` страницы;
- `fetch` с `cache: 'no-store'` (в Next 15 fetch по умолчанию не кэшируется, но маршрут остаётся статическим, пока нет динамических API);
- `export const dynamic = 'force-dynamic'` или `revalidate = 0`.

Аналоги Pages Router: `generateStaticParams` ≈ `getStaticPaths`; `export const revalidate = 60` или `fetch(url, { next: { revalidate: 60 } })` ≈ ISR; `dynamicParams` ≈ `fallback`; `revalidatePath`/`revalidateTag` ≈ on-demand ISR. Функции `getStaticProps`/`getServerSideProps` в App Router нет — данные читаются прямо в async Server Components.

### 6.6 Cache Components (Next.js 16)

С флагом `cacheComponents: true` логика переворачивается: данные **динамические по умолчанию**, кэширование явное, гранулярность — компонент.

- **Статическое автоматически:** синхронный код, импорты, вычисления без рантайм-данных — попадает в статическую оболочку при сборке.
- **Кэшируемое:** `'use cache'` на файле, компоненте или функции. Время жизни — `cacheLife('minutes' | 'hours' | 'days' | …)`, теги — `cacheTag()`. Внутри `'use cache'` нельзя читать `cookies()`/`headers()`/`searchParams` — их передают аргументами. Есть варианты `'use cache: remote'` и `'use cache: private'`.
- **Динамическое:** всё, что читает рантайм-данные, обязано быть внутри `<Suspense>` — это «дыры» PPR, которые стримятся в том же ответе.
- **Инвалидация:** `revalidateTag(tag, profile)` — фоново (stale-while-revalidate), `updateTag(tag)` — сразу, чтобы пользователь в том же запросе увидел свои изменения (только в Server Actions).
- `unstable_cache` и `experimental.ppr` заменены; сегментные конфиги вроде `dynamic`/`revalidate` заменяются `'use cache'` + `cacheLife`. Не работает в Edge-рантайме и при `output: 'export'`.

### 6.7 Стриминг и loading.tsx

`loading.tsx` автоматически оборачивает страницу сегмента в `<Suspense>`. Внутри можно ставить свои `<Suspense>`. Порядок в ответе: сначала оболочка + fallback-и, потом по мере готовности — куски HTML с инструкцией вставить их на место и соответствующие строки payload. Клиентские компоненты внутри каждого куска гидратируются независимо (селективная гидратация).

### 6.8 Хуки в App Router при SSG и SSR

В Client Component всё как в Pages Router: на сервере рендер с начальным `useState`, `useEffect` — только в браузере, обращение к `window` при рендере — mismatch. `useSearchParams()` на статическом маршруте заставляет компонент до ближайшего `<Suspense>` рендериться только на клиенте (без Suspense вся страница уйдёт в клиентский рендеринг до этой границы, а `next build` выдаст ошибку/предупреждение). В Server Component хуков состояния и эффектов нет вообще.

## 7. Pages vs App: что приходит в первом запросе

Главное различие: в Pages Router в браузер уходит JS **каждого** компонента страницы; в App Router — только компонентов за границей `'use client'`. HTML в обоих случаях полный, если данные получены на сервере.

### 7.1 Компонент × режим: HTML, JS, данные

| Роутер | Компонент и режим | В HTML первого ответа | JS в бандле | Данные для гидратации | Гидратируется |
| --- | --- | --- | --- | --- | --- |
| Pages | Любой компонент на SSG/ISR-странице | Да, сгенерирован при сборке | Да | `__NEXT_DATA__` (props из `getStaticProps`) | Да |
| Pages | Любой компонент на SSR-странице | Да, на каждый запрос | Да | `__NEXT_DATA__` (props из `getServerSideProps`) | Да |
| Pages | Компонент с `useState`/`useEffect` | Да, начальное состояние; результат эффекта — нет | Да | — | Да |
| Pages / App | `dynamic(..., { ssr: true })` (по умолчанию) | Да | Да, отдельным чанком, грузится сразу | Как у родителя | Да |
| Pages / App | `dynamic(..., { ssr: false })` | Нет, только `loading` | Да, отдельный чанк, рендер в браузере | — | Нет, монтируется на клиенте |
| App | Server Component на статическом маршруте | Да, при сборке | **Нет** | Его результат лежит в RSC payload | Нет |
| App | Server Component на динамическом маршруте | Да, на каждый запрос | Нет | RSC payload | Нет |
| App | Server Component в `<Suspense>` (PPR-дыра / стриминг) | Сначала fallback, затем досылается в том же ответе | Нет | RSC payload, по частям | Нет |
| App | Client Component на статическом маршруте | Да, при сборке, начальное состояние | Да | Ссылка на модуль + сериализованные пропсы в RSC payload | Да |
| App | Client Component с fetch в `useEffect` | Только начальное состояние/скелетон | Да | Запрос к API после гидратации | Да |
| App | Client Component с `useSearchParams()` на статическом маршруте | Fallback ближайшего `<Suspense>` | Да | — | Рендерится на клиенте до границы |
| App | Server Component, переданный как `children` в Client Component | Да | Нет | RSC payload | Нет (клиентская обёртка — да) |

### 7.2 Роутеры целиком

| Аспект | Pages Router | App Router |
| --- | --- | --- |
| Компоненты по умолчанию | Все в бандле и гидратируются | Server Components: без JS и гидратации |
| Где получают данные | `getStaticProps` / `getServerSideProps` на уровне страницы | async Server Components где угодно в дереве |
| Как данные доходят до клиента | JSON в `__NEXT_DATA__` | RSC payload в `self.__next_f` |
| Навигация запрашивает | JS-чанк + `/_next/data/…json` | RSC payload только изменившихся сегментов |
| Layout при навигации | `_app` общий, вложенных layout нет | Вложенные layout сохраняют состояние |
| Гранулярность стратегии | Страница | Маршрут (Next 13–15) / компонент (Next 16 + Cache Components) |
| Стриминг и Suspense на сервере | Нет | Да (`loading.tsx`, `<Suspense>`) |
| Мутации | API-роуты | Server Actions + route handlers |
| Типичный размер JS | Растёт со всей страницей | Растёт только с клиентскими компонентами |

### 7.3 Пример на одной странице блога

Статья (markdown → HTML) + кнопка «лайк» + блок комментариев.

- **Pages + SSG:** HTML всей страницы; в бандле — статья, кнопка, комментарии и, если markdown парсится в компоненте, сам парсер; markdown-текст дублируется в `__NEXT_DATA__`.
- **App + SSG:** HTML всей страницы; в бандле — только `LikeButton` и `Comments` (`'use client'`); статья и парсер остаются на сервере, результат статьи — в RSC payload.

## 8. next/dynamic, ssr: true/false и типичные ловушки

`next/dynamic` — это `React.lazy` + `Suspense` + поддержка SSR и предзагрузки чанков. Он решает **одну** задачу — вынос кода в отдельный чанк; флаг `ssr` решает **вторую** — рендерить ли компонент на сервере.

### 8.1 ssr: true (по умолчанию)

```tsx
const Reviews = dynamic(() => import('./Reviews'), { loading: () => <Skeleton /> })
```

- Компонент **рендерится на сервере** и есть в HTML.
- Его код вынесен в отдельный чанк, но Next знает, что он понадобится для гидратации, и подключает этот чанк сразу. Экономии на первой загрузке почти нет.
- Выигрыш появляется, когда компонент рендерится **по условию** (модалка, вкладка, админ-панель): пока условие ложно, чанк не качается.

### 8.2 ssr: false

```tsx
'use client' // в App Router обязательно: в Server Component ssr:false запрещён
const Map = dynamic(() => import('./Map'), { ssr: false, loading: () => <div style={{ height: 400 }} /> })
```

- На сервере на месте компонента рендерится только `loading` (или ничего).
- В браузере после гидратации качается чанк и компонент монтируется — никакой гидратации, значит, и никакого mismatch.
- **Когда:** библиотеки, которые трогают `window`/`document` при импорте (Leaflet, некоторые графики и редакторы), UI, зависящий от `localStorage`/размеров окна, тяжёлые виджеты ниже первого экрана.
- **Цена:** содержимого нет в HTML (SEO), задержка появления, CLS, если `loading` не держит размер.

### 8.3 Нюансы в App Router

- `dynamic()` для **Server Component** не делит его код (он и так не идёт в браузер) — лениво грузятся только клиентские компоненты внутри него.
- Именованный экспорт: `dynamic(() => import('./charts').then(m => m.LineChart))`.
- Подгрузка по действию: рендерить dynamic-компонент только после клика или делать `await import('lib')` прямо в обработчике.
- Альтернативы `ssr: false` для мелочей: флаг `mounted` через `useEffect`, `useSyncExternalStore` с серверным снапшотом, `suppressHydrationWarning` для одного элемента (например, времени).

### 8.4 Ловушки

- **«`'use client'` = CSR».** Нет: такой компонент пререндерится на сервере и гидратируется. Только-клиентский рендер — это `ssr: false`, `useEffect` или `useSearchParams` без серверного значения.
- **Hydration mismatch.** Причины: `window`/`localStorage` в рендере, `Date.now()`/`Math.random()`, форматирование дат по локали/часовому поясу, `typeof window !== 'undefined'` в JSX, невалидная вложенность (`<p><div>`), расширения браузера.
- **`'use client'` слишком высоко** (на странице или layout) — весь подграф уходит в бандл. Опускайте границу к интерактивным листьям; провайдеры контекста — отдельный клиентский файл, `children` остаются серверными.
- **Огромные пропсы в Client Component** — сериализуются в payload (и в HTML). Передавайте только нужные поля.
- **Секреты.** Импорт серверного модуля в клиентский файл тянет его в бандл. Используйте `server-only`; переменные окружения без `NEXT_PUBLIC_` в браузере — `undefined`.
- **Отравление статики.** `cookies()`/`headers()` в корневом layout делает динамическими все маршруты (без Cache Components).
- **SEO-контент через fetch в `useEffect`** — его нет в HTML. Получайте на сервере.
- **`getServerSideProps` для редко меняющихся данных** — платите SSR на каждый запрос там, где хватило бы ISR.
- **`fallback: true` без обработки `router.isFallback`** — падение на пустых props.
- **Barrel-файлы и большие UI-библиотеки** раздувают клиентские чанки; помогает `optimizePackageImports` и прямые импорты.

## 9. Шпаргалка и самопроверка

### Пять правил, которые объясняют почти всё

1. Стратегия решает, **кто и когда делает HTML**; RSC и острова решают, **сколько JS гидратировать**. Это две независимые оси.
2. Всё, что рендерится на сервере и при этом нужно в браузере, приходит **дважды**: как HTML и как данные для гидратации (`__NEXT_DATA__` или RSC payload).
3. В Pages Router бандл = все компоненты страницы. В App Router бандл = только то, что за `'use client'`.
4. `'use client'` ≠ клиентский рендеринг. Без SSR компонент рендерится только при `ssr: false` или если данные берутся в эффекте/из браузерных API.
5. Одно динамическое чтение (`cookies`, `headers`, `searchParams`, no-store) без Suspense делает динамическим весь маршрут; в Next 16 его нужно обернуть в `<Suspense>`, и тогда оно становится PPR-дырой.

### Соответствие API

| Задача | Pages Router | App Router (Next 13–15) | App Router + Cache Components (Next 16) |
| --- | --- | --- | --- |
| SSG | `getStaticProps` | Статический маршрут по умолчанию | Статическая оболочка / `'use cache'` |
| Динамические пути | `getStaticPaths` | `generateStaticParams` | `generateStaticParams` |
| Неизвестные пути | `fallback` | `dynamicParams` | `dynamicParams` |
| ISR | `revalidate` в `getStaticProps` | `export const revalidate`, `next.revalidate` в fetch | `cacheLife(...)` |
| On-demand ISR | `res.revalidate(path)` | `revalidatePath`, `revalidateTag` | `revalidateTag(tag, profile)`, `updateTag` |
| SSR | `getServerSideProps` | `cookies()`/`headers()`/`force-dynamic` | Рантайм-данные внутри `<Suspense>` |
