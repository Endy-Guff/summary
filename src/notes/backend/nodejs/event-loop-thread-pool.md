# Event Loop и Thread Pool в Node.js — конспект

## 1. Общая картина: из чего состоит Node.js

Главная мысль: ваш JavaScript выполняется в одном потоке, но сам процесс Node.js многопоточный. Event loop — это цикл в главном потоке, который решает, какой колбэк выполнить следующим. Thread pool — это набор фоновых потоков, куда уходит работа, которую ОС не умеет делать асинхронно.

Node.js состоит из нескольких слоёв:

| Слой | Что делает | Язык |
| --- | --- | --- |
| Ваш код и npm-пакеты | Бизнес-логика | JS |
| Стандартная библиотека Node (`fs`, `net`, `http`, `crypto`…) | JS-обёртки над нативными функциями | JS |
| Биндинги (C++ bindings) | Мост между JS и C/C++ | C++ |
| V8 | Компилирует и выполняет JS, управляет heap и GC, держит очередь микрозадач Promise | C++ |
| libuv | Event loop, асинхронный I/O, таймеры, thread pool, сигналы, дочерние процессы | C |
| Прочее: llhttp, OpenSSL, zlib, c-ares, ICU | Парсинг HTTP, криптография, сжатие, DNS, интернационализация | C/C++ |

Ключевое разделение ролей:

- **V8 не знает ничего про I/O, таймеры и event loop.** Он только выполняет JS. `setTimeout` — это не часть языка JavaScript, это API, которое предоставляет Node (через libuv).
- **libuv — это и есть event loop.** Он ждёт событий от ОС, запускает таймеры и раздаёт работу thread pool.
- **Node склеивает их:** когда libuv сообщает «данные пришли», Node вызывает в V8 ваш JS-колбэк.

Сколько потоков на самом деле в процессе Node (можно проверить через `top -H -p <pid>` или Activity Monitor):

- 1 главный поток — event loop + выполнение вашего JS;
- 4 потока thread pool libuv по умолчанию (создаются лениво, при первой задаче);
- несколько потоков V8 — фоновая сборка мусора, фоновая компиляция (оптимизирующий компилятор);
- служебные потоки Node (например, для инспектора/платформы).

Отсюда фраза «Node однопоточный» верна только про выполнение JS: в один момент времени в одном изоляте выполняется ровно одна функция JS, и никто её не прервёт, пока она не вернёт управление.

## 2. Базовые понятия: стек, heap, очереди

Event loop берёт следующий колбэк из очереди только тогда, когда стек вызовов пуст. Это правило «run-to-completion» объясняет почти всё поведение Node.

- **Call stack (стек вызовов)** — где выполняется текущий синхронный код. Пока в стеке что-то есть, event loop стоит и ждёт.
- **Heap (куча)** — память под объекты, замыкания, буферы JS. Управляется сборщиком мусора V8. (`Buffer` хранит данные вне JS-heap, но управляется оттуда же.)
- **Очереди макрозадач** — у libuv нет одной общей очереди: у каждой фазы своя (таймеры в min-heap по времени, I/O-колбэки, `setImmediate`, close-колбэки).
- **Очереди микрозадач** — две штуки: очередь `process.nextTick` (принадлежит Node) и очередь микрозадач V8 (Promise, `queueMicrotask`).

### Что значит «асинхронный» вызов

Когда вы вызываете `fs.readFile(path, cb)`:

1. JS-функция вызывает C++-биндинг, тот передаёт задачу в libuv.
2. libuv отдаёт чтение файла в thread pool (для файлов) или регистрирует сокет в epoll/kqueue/IOCP (для сети).
3. `readFile` сразу возвращается, стек раскручивается, ваш код идёт дальше.
4. Когда операция завершилась, libuv в нужной фазе цикла вызывает внутренний колбэк Node, а тот — ваш `cb` (уже в главном потоке).
5. После каждого такого колбэка Node опустошает очереди микрозадач.

### Когда процесс завершается

Цикл крутится, пока есть «живые» (ref'нутые) хэндлы и запросы: активные таймеры, открытые серверы и сокеты, незавершённые операции fs/dns и т.д. Когда их нет — цикл выходит, срабатывает событие `beforeExit`, затем `exit`.

- `timer.unref()` / `server.unref()` / `socket.unref()` — «не держи процесс ради меня».
- `ref()` — вернуть обратно.
- Неразрешённый Promise сам по себе процесс **не держит**: если ничего больше не ждёт, процесс просто завершится.

## 3. Фазы event loop

Одна итерация цикла («тик» libuv) проходит шесть фаз по кругу, и у каждой фазы своя очередь колбэков. Между любыми двумя колбэками Node опустошает микрозадачи ([раздел 4](#4-микрозадачи-nexttick-promise-queuemicrotask)).

| # | Фаза | Что выполняется | Кто туда попадает |
| --- | --- | --- | --- |
| 1 | **timers** | Колбэки таймеров, чьё время наступило | `setTimeout`, `setInterval` |
| 2 | **pending callbacks** | I/O-колбэки, отложенные с прошлой итерации | Некоторые системные ошибки (например, `ECONNREFUSED` на TCP) |
| 3 | **idle, prepare** | Внутренние нужды Node/libuv | Не ваш код |
| 4 | **poll** | Ждём новых I/O-событий и выполняем их колбэки | Почти всё: сокеты, ответы thread pool (fs, dns.lookup, crypto, zlib) |
| 5 | **check** | Колбэки `setImmediate` | `setImmediate` |
| 6 | **close callbacks** | Колбэки закрытия | `socket.on('close')`, `handle.close()` |

### timers

- Таймеры хранятся в min-heap, отсортированы по времени срабатывания.
- Задержка — это **минимум**, а не гарантия. `setTimeout(fn, 100)` выполнится не раньше чем через 100 мс, но может позже, если цикл занят.
- `setTimeout(fn, 0)` на самом деле `setTimeout(fn, 1)`: Node приводит 0 (и всё больше 2³¹−1 или не число) к 1 мс.
- libuv кэширует «текущее время» в начале итерации (`uv_now`), поэтому таймеры сравниваются с ним, а не с реальным временем на каждом шаге.

### poll — самая важная фаза

Здесь цикл проводит большую часть жизни. Порядок такой:

1. Вычисляется таймаут ожидания:
   - есть колбэки `setImmediate` или закрывающиеся хэндлы → таймаут 0 (не ждём);
   - иначе есть таймеры → ждём до ближайшего таймера;
   - иначе есть активные хэндлы → ждём бесконечно (процесс «спит», CPU ≈ 0%);
   - нет ничего живого → цикл завершается.
2. Вызов `epoll_wait` / `kevent` / `GetQueuedCompletionStatus` с этим таймаутом — поток блокируется в ядре до события.
3. Для каждого готового события выполняется колбэк (в том числе колбэки завершённых задач thread pool — пул будит цикл через внутренний `uv_async`).
4. Если есть `setImmediate` — переходим в check; иначе по таймауту переходим дальше и возвращаемся к таймерам.

Именно здесь объясняется, почему «спящий» Node-сервер не грузит CPU: он висит в системном вызове ожидания.

### check

Выполняются **все** колбэки `setImmediate`, накопленные к началу фазы. Если внутри колбэка вызвать новый `setImmediate`, он попадёт на **следующую** итерацию — так `setImmediate` не может застопорить цикл (в отличие от `nextTick`).

### close callbacks

События `'close'`, если хэндл закрыт резко (`socket.destroy()`). Обычное закрытие может отдать `'close'` через `process.nextTick`.

### Нюанс про новые версии libuv

В libuv 1.45+ (Node 20 и новее) обработку таймеров перенесли в конец итерации — сразу после close callbacks (плюс один запуск таймеров перед входом в цикл). По кругу порядок фаз тот же: timers → pending → idle/prepare → poll → check → close → timers… Меняется лишь то, где формально «начинается» итерация. Классическая схема из документации Node по-прежнему верна для понимания.

### Схема одной итерации

```text
   ┌───────────────────────────┐
┌─>│          timers           │  setTimeout / setInterval
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     pending callbacks     │  отложенные I/O-ошибки
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │       idle, prepare       │  внутреннее
│  └─────────────┬─────────────┘      ┌───────────────┐
│  ┌─────────────┴─────────────┐      │   incoming:   │
│  │           poll            │<─────┤  connections, │
│  └─────────────┬─────────────┘      │   data, etc.  │
│  ┌─────────────┴─────────────┐      └───────────────┘
│  │           check           │  setImmediate
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
└──┤      close callbacks      │  'close'
   └───────────────────────────┘
   (после КАЖДОГО колбэка: nextTick-очередь, затем Promise-микрозадачи)
```

## 4. Микрозадачи: nextTick, Promise, queueMicrotask

Микрозадачи — это не фаза event loop, а «вставка» между колбэками: как только текущий колбэк закончился и стек пуст, Node полностью опустошает сначала очередь `nextTick`, затем очередь Promise, и повторяет, пока обе не опустеют.

| Механизм | Чья очередь | Приоритет | Типичное применение |
| --- | --- | --- | --- |
| `process.nextTick(fn)` | Node | Самый высокий | Отложить на «сразу после текущей операции», выдать событие после того, как пользователь успел подписаться |
| `Promise.then` / `await` | V8 | После всех nextTick | Обычный асинхронный код |
| `queueMicrotask(fn)` | V8 (та же, что Promise) | Как Promise | Стандартный (как в браузере) способ поставить микрозадачу |

### Алгоритм опустошения

```text
после каждого макро-колбэка:
  повторять:
    пока nextTick-очередь не пуста → выполнить следующий nextTick
    опустошить Promise-очередь V8 целиком
        (новые Promise-микрозадачи выполняются в этом же проходе;
         новые nextTick ждут следующего круга)
  пока обе очереди не пусты
```

Важные следствия:

- **С Node 11** микрозадачи выполняются после **каждого** отдельного колбэка `setTimeout`/`setImmediate`, а не после всей фазы — как в браузере. В Node ≤10 было иначе, поэтому старые статьи иногда показывают другой вывод.
- **Рекурсивный `nextTick` вешает цикл.** `function f(){ process.nextTick(f) }` никогда не даст циклу дойти до I/O — сервер перестанет отвечать. Бесконечная цепочка Promise делает то же самое. Рекурсивный `setImmediate` безопасен: каждый новый уходит на следующую итерацию.
- `await` внутри async-функции — это синтаксический сахар над `.then`: всё после `await` — это микрозадача.

### Подвох: CommonJS vs ES-модули

```js
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
```

- В CommonJS-файле (`.js`/`.cjs`): `nextTick`, затем `promise`.
- В ES-модуле (`.mjs` или `"type": "module"`): `promise`, затем `nextTick`. Модуль выполняется как часть асинхронной загрузки, и V8 опустошает свою очередь микрозадач раньше, чем Node доходит до очереди `nextTick`.

Вывод: не стройте логику на порядке между `nextTick` и Promise. Документация Node сама советует предпочитать `queueMicrotask` вместо `process.nextTick` для нового кода.

## 5. Порядок выполнения на примерах

Общее правило: синхронный код → `nextTick` → Promise/`queueMicrotask` → фазы цикла (таймеры, poll, `setImmediate`…). Все примеры ниже — CommonJS.

### Пример 1. Всё вместе

```js
console.log('1 sync');
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('4 promise'));
process.nextTick(() => console.log('3 nextTick'));
queueMicrotask(() => console.log('5 microtask'));
console.log('2 sync');
```

Вывод: `1 sync`, `2 sync`, `3 nextTick`, `4 promise`, `5 microtask`, а затем `timeout` и `immediate` — **в любом порядке**.

### Пример 2. Почему timeout vs immediate непредсказуем в главном модуле

`setTimeout(fn, 0)` — это 1 мс. Если с момента запуска таймера до входа в фазу timers прошло ≥ 1 мс (зависит от загрузки машины), таймер уже «созрел» и выполнится первым. Если меньше — цикл пройдёт timers впустую, дойдёт до check, и первым будет `setImmediate`.

### Пример 3. Внутри I/O-колбэка порядок гарантирован

```js
const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
```

Всегда: `immediate`, затем `timeout`. Колбэк выполняется в фазе poll, следующая фаза — check, а до таймеров цикл доберётся только на следующем круге.

### Пример 4. Микрозадачи между таймерами

```js
setTimeout(() => {
  console.log('t1');
  Promise.resolve().then(() => console.log('p1'));
}, 0);
setTimeout(() => console.log('t2'), 0);
```

Node 11+: `t1`, `p1`, `t2` — микрозадачи выполняются после каждого колбэка таймера.

### Пример 5. async/await

```js
async function a() {
  console.log('a1');
  await null;
  console.log('a2');
}
console.log('s1');
a();
console.log('s2');
```

Вывод: `s1`, `a1`, `s2`, `a2`. Тело async-функции до первого `await` выполняется синхронно; остаток — микрозадача.

### Пример 6. nextTick внутри Promise

```js
Promise.resolve().then(() => {
  console.log('p1');
  process.nextTick(() => console.log('tick'));
}).then(() => console.log('p2'));
```

Вывод: `p1`, `p2`, `tick`. Очередь Promise принадлежит V8, и V8 опустошает её целиком, включая `p2`, добавленный по ходу. Только потом Node возвращается к очереди `nextTick`.

### Когда что использовать

| Нужно | Используйте |
| --- | --- |
| Выполнить «сразу после текущего синхронного кода», до любого I/O | `queueMicrotask` (или `process.nextTick`) |
| Отдать управление циклу, дать обработаться I/O, разбить длинную работу на куски | `setImmediate` |
| Выполнить через время | `setTimeout` / `setInterval` |
| Промисифицированная задержка | `await setTimeout(ms)` из `node:timers/promises` |

## 6. Thread pool libuv

Thread pool — это 4 фоновых потока (по умолчанию), которые выполняют операции, не имеющие нормального асинхронного API в ОС, или тяжёлые для CPU. Пул один на весь процесс и общий для главного потока и всех `worker_threads`.

### Как устроен

1. Главный поток кладёт задачу (`uv_work_t`) в общую FIFO-очередь пула.
2. Свободный поток пула берёт задачу и выполняет её **блокирующе** (например, обычный `read()`).
3. Результат кладётся в очередь завершённых, поток пула «будит» event loop через `uv_async_send`.
4. В фазе poll главный поток выполняет колбэк завершения, и Node вызывает ваш JS-колбэк / разрешает Promise.

Потоки создаются лениво — при первой задаче. Ваш JS в пуле **никогда** не выполняется: там работает только нативный C/C++ код.

### Что идёт в пул, а что нет

| Идёт в thread pool | НЕ идёт в thread pool |
| --- | --- |
| Почти все асинхронные `fs.*` и `fs/promises` (read, write, stat, open, readdir…) | Сеть: `net`, `http`, `https`, `tls`, TCP/UDP, `fetch` — через epoll/kqueue/IOCP |
| `dns.lookup()` — его использует `http.get`, `net.connect` и т.д. по умолчанию | `dns.resolve*()` / `dns.promises.Resolver` — c-ares, работает через сокеты |
| `crypto`: `pbkdf2`, `scrypt`, `randomBytes`/`randomFill` (асинхронные), `generateKeyPair`, `hkdf`, часть `crypto.subtle` | Таймеры, `setImmediate`, Promise |
| `zlib` асинхронные (`gzip`, `deflate`, `brotliCompress`…) | `child_process`, пайпы, TTY, сигналы |
| Нативные аддоны через `napi_create_async_work` | `fs.watch` (inotify / FSEvents / ReadDirectoryChangesW) |

Синхронные версии (`fs.readFileSync`, `crypto.pbkdf2Sync`, `zlib.gzipSync`) идут **не в пул, а блокируют главный поток**.

### Размер пула: UV_THREADPOOL_SIZE

- По умолчанию 4, максимум 1024 (в старых libuv — 128).
- Задаётся переменной окружения **до** первой задачи пулу. Надёжно — при запуске: `UV_THREADPOOL_SIZE=16 node app.js`.
- Присваивание `process.env.UV_THREADPOOL_SIZE = 16` в самом начале кода обычно работает на Linux/macOS, но на Windows не срабатывает — не полагайтесь на это.
- Узнать число ядер: `os.availableParallelism()` (Node 18.14+) или `os.cpus().length`.

Как выбирать:

- CPU-задачи (crypto, zlib) — больше потоков, чем ядер, не ускорит, а добавит переключений контекста.
- Дисковый I/O и `dns.lookup` в основном ждут, поэтому их пул можно делать больше ядер (8–64), если они упираются в очередь.
- Каждый поток — это память под стек и переключения; ставьте значение по замерам, а не «на всякий случай 128».

### Эксперимент: увидеть пул своими глазами

```js
const crypto = require('crypto');
const start = Date.now();
for (let i = 1; i <= 6; i++) {
  crypto.pbkdf2('secret', 'salt', 300_000, 64, 'sha512', () => {
    console.log(`hash ${i}: ${Date.now() - start} ms`);
  });
}
```

С размером пула 4 первые четыре хэша завершатся почти одновременно (за время T), а 5-й и 6-й — примерно за 2T: они ждали свободного потока. Запустите с `UV_THREADPOOL_SIZE=6` — все шесть закончат примерно одновременно (если ядер хватает).

### Типичные проблемы

- **Голодание пула (starvation).** Очередь общая и FIFO. Медленные операции (файлы на сетевом диске, тяжёлый `scrypt`, сотни `dns.lookup` при медленном DNS) занимают все 4 потока, и даже быстрый `fs.stat` ждёт в очереди.
- **DNS как скрытое узкое место.** Каждый исходящий HTTP-запрос к домену по умолчанию делает `dns.lookup` через пул. Под нагрузкой это ограничивает исходящие запросы. Лечение: keep-alive (`http.Agent({ keepAlive: true })`, в Node 19+ включён по умолчанию для глобального агента), кэш DNS, `dns.resolve` вместо `lookup` там, где допустимо.
- **Огромный `fs.readFile`** читает файл кусками, но занимает поток надолго. Для больших файлов лучше `fs.createReadStream`.

### io_uring (Linux)

libuv 1.45+ умеет выполнять часть файловых операций через io_uring, минуя пул. В Node это было отключено по умолчанию из-за проблем безопасности (включается переменной `UV_USE_IO_URING=1`). На практике считайте, что файловые операции идут через thread pool.

## 7. Сетевой I/O: почему 10 000 соединений не требуют 10 000 потоков

Сеть в Node не использует thread pool: главный поток регистрирует все сокеты в механизме уведомлений ядра и одним системным вызовом ждёт событий сразу по всем. Это и есть причина, по которой Node хорошо держит тысячи одновременных соединений.

| ОС | Механизм | Модель |
| --- | --- | --- |
| Linux | epoll | Готовность: «в сокете есть данные, читай» |
| macOS, FreeBSD | kqueue | Готовность |
| Windows | IOCP | Завершение: «операция уже выполнена, вот результат» |
| SunOS | event ports | Готовность |

Как проходит HTTP-запрос к серверу:

1. `server.listen()` — серверный сокет регистрируется в epoll.
2. Пришло подключение → фаза poll получает событие, libuv делает `accept()`, Node создаёт `net.Socket`.
3. Пришли данные → событие готовности, неблокирующий `read()`, llhttp парсит байты, Node вызывает ваш обработчик `(req, res)`.
4. `res.end()` → неблокирующий `write()`; если буфер ядра полон, libuv подписывается на «можно писать» и допишет позже.

### Сравнение двух путей

|  | Сеть (ОС) | Thread pool |
| --- | --- | --- |
| Ограничение параллельности | Практически нет (лимиты файловых дескрипторов, `ulimit -n`) | Размер пула (4 по умолчанию) |
| Где ждём | В ядре, один вызов на все сокеты | Каждый поток блокируется на своей операции |
| Почему так | Для сокетов у ОС есть неблокирующий API | Для обычных файлов и `getaddrinfo` портабельного асинхронного API нет |

Почему файлы не через epoll: для обычных файлов epoll всегда отвечает «готово», а чтение с диска всё равно блокирует. Поэтому libuv просто выполняет блокирующий вызов в отдельном потоке.

## 8. Блокировка event loop: причины, симптомы, диагностика

Любой синхронный код дольше нескольких миллисекунд останавливает весь процесс: пока он выполняется, не обрабатываются ни запросы, ни таймеры, ни ответы thread pool. Это главная причина «Node тормозит».

### Типичные причины

- Синхронные API в обработчиках запросов: `readFileSync`, `execSync`, `pbkdf2Sync`, `zlib.*Sync`.
- `JSON.parse` / `JSON.stringify` больших объектов (десятки МБ — это сотни миллисекунд).
- Тяжёлые вычисления: циклы по миллионам элементов, сортировка огромных массивов, обработка изображений на чистом JS.
- Катастрофический backtracking в регулярных выражениях (ReDoS), например `/(a+)+$/` на длинной строке.
- Бесконечные цепочки `nextTick` / Promise ([раздел 4](#4-микрозадачи-nexttick-promise-queuemicrotask)).
- Долгие паузы сборщика мусора из-за огромного heap.

### Симптомы

- Растёт задержка всех запросов сразу, а не только «тяжёлых».
- Таймеры срабатывают с большим опозданием.
- Падают health-check'и, хотя CPU у процесса ~100% на одном ядре.

### Как измерять

```js
const { monitorEventLoopDelay, performance } = require('node:perf_hooks');

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();

let last = performance.eventLoopUtilization();
setInterval(() => {
  const elu = performance.eventLoopUtilization(last);
  last = performance.eventLoopUtilization();
  console.log({
    p99_ms: h.percentile(99) / 1e6,   // задержка цикла, нс → мс
    max_ms: h.max / 1e6,
    utilization: elu.utilization.toFixed(2), // 0..1, доля времени «занят»
  });
  h.reset();
}, 5000).unref();
```

- **Event loop delay (лаг)** — насколько опаздывает цикл. Ориентир: p99 в единицы-десятки мс — нормально, сотни мс — проблема.
- **Event loop utilization (ELU)** — доля времени, когда цикл не простаивает в poll. Близко к 1 — цикл перегружен, пора масштабировать или выносить работу.

### Инструменты поиска виновника

| Инструмент | Что даёт |
| --- | --- |
| `node --cpu-prof app.js` | Профиль CPU (`.cpuprofile`), открывается в Chrome DevTools |
| `node --inspect` + Chrome DevTools | Живой профайлер, heap snapshots |
| `node --trace-sync-io` | Предупреждения о синхронных I/O после первого тика |
| `node --prof` + `--prof-process` | Низкоуровневый профиль V8 |
| Flame graph (0x, clinic.js flame) | Где проводится время |
| APM-системы | Лаг и ELU в продакшене |

## 9. Управление: как не блокировать цикл и использовать все ядра

Выбор инструмента зависит от того, что за работа: I/O отдаём циклу и пулу, тяжёлый JS-CPU — в worker_threads, а масштаб на все ядра — через несколько процессов.

| Инструмент | Что это | Когда использовать |
| --- | --- | --- |
| Разбиение на куски (`setImmediate`) | Та же нить, работа порциями | Умеренные вычисления, когда нельзя выносить в отдельный поток |
| `worker_threads` | Отдельный поток со своим V8-изолятом и своим event loop | CPU-тяжёлый JS: парсинг, обработка изображений, ML-инференс на JS |
| `child_process` (`spawn`, `fork`, `exec`) | Отдельный процесс ОС | Внешние программы, изоляция падений, другой язык |
| `cluster` / PM2 / несколько контейнеров | N процессов Node, слушающих один порт | Масштабирование HTTP-сервера на все ядра |
| `UV_THREADPOOL_SIZE` | Размер пула libuv | Много fs / crypto / zlib / `dns.lookup` упирается в очередь пула |

### Разбиение длинной задачи

```js
async function processAll(items) {
  const CHUNK = 1000;
  for (let i = 0; i < items.length; i += CHUNK) {
    for (const item of items.slice(i, i + CHUNK)) heavy(item);
    await new Promise(setImmediate); // отдаём цикл I/O между кусками
  }
}
```

Именно `setImmediate`, а не `Promise.resolve()` или `nextTick`: микрозадачи не отдают управление I/O, цикл так и останется заблокированным.

### worker_threads — минимальный пример

```js
// main.js
const { Worker } = require('node:worker_threads');
function runTask(data) {
  return new Promise((resolve, reject) => {
    const w = new Worker('./worker.js', { workerData: data });
    w.once('message', resolve);
    w.once('error', reject);
  });
}

// worker.js
const { parentPort, workerData } = require('node:worker_threads');
parentPort.postMessage(heavyCompute(workerData));
```

Что важно знать:

- У каждого воркера свой изолят, heap, event loop и очереди микрозадач. Глобальные переменные не общие.
- Данные передаются копированием (structured clone). Без копирования — передать `ArrayBuffer` через transfer list или делить `SharedArrayBuffer` (синхронизация через `Atomics`).
- Создание воркера стоит десятки миллисекунд и память: **держите пул воркеров**, а не создавайте по воркеру на запрос (готовая библиотека — `piscina`).
- Thread pool libuv общий для всех воркеров процесса.
- Для I/O воркеры не нужны — асинхронный I/O и так не блокирует главный поток.

### cluster

```js
const cluster = require('node:cluster');
const os = require('node:os');
if (cluster.isPrimary) {
  for (let i = 0; i < os.availableParallelism(); i++) cluster.fork();
  cluster.on('exit', () => cluster.fork()); // перезапуск упавших
} else {
  require('./server'); // каждый процесс слушает один и тот же порт
}
```

У каждого процесса свой event loop и свой thread pool (4 потока на процесс). В контейнерах (Kubernetes) часто проще запускать по одному процессу на контейнер и масштабировать репликами.

### Лучшие практики

1. Никаких `*Sync`-методов в коде, который обслуживает запросы (в старте приложения — можно).
2. Большие данные — потоками (`stream.pipeline`), а не целиком в память; соблюдайте backpressure.
3. Ограничивайте конкурентность: не запускайте 10 000 `fs`-операций или запросов одновременно (`p-limit` или пачки).
4. Проверяйте регулярные выражения на ReDoS, ограничивайте размер входных данных (тело запроса, JSON).
5. Мониторьте event loop delay и ELU в продакшене.
6. Ставьте таймауты и отменяйте лишнюю работу (`AbortController`, `signal` в `fetch`, `fs`, `timers/promises`).
7. Используйте keep-alive для исходящих HTTP, чтобы снизить нагрузку на `dns.lookup` и пул.
8. Не используйте `nextTick` для «отдачи управления» — для этого `setImmediate`.

## 10. Шпаргалка и самопроверка

### Десять фактов, которые нужно помнить

1. JS выполняется в одном потоке; процесс Node — многопоточный.
2. Event loop — это libuv; V8 только выполняет JS.
3. Фазы по кругу: timers → pending → idle/prepare → poll → check → close.
4. После каждого колбэка: все `nextTick`, затем все Promise-микрозадачи.
5. `setTimeout(fn, 0)` = 1 мс и «не раньше чем», а не «ровно через».
6. Внутри I/O-колбэка `setImmediate` всегда раньше `setTimeout(…, 0)`.
7. Сеть — через epoll/kqueue/IOCP, без пула и почти без лимита параллельности.
8. Thread pool (4 потока, `UV_THREADPOOL_SIZE`): fs, `dns.lookup`, crypto (pbkdf2, scrypt…), zlib.
9. Любой долгий синхронный код блокирует всё; CPU-работу — в `worker_threads`.
10. Метрики здоровья: event loop delay и event loop utilization.
